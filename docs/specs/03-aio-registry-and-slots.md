# Spec 03: Synthesized AIO Model Registry & Task Slots

## 1. Zero Hardcoded Models
Bistre ships zero hardcoded model IDs or pricing tables in application binaries. The registry synthesizer in `crates/bistre-core` merges live and signed Track-A catalog layers deterministically:
1. Signed Baseline Catalog Pack (Track A): Offline `minisign`-verified snapshot shipped/updated independently of app binaries.
2. Upstream Catalog Sources (every output kind, not text only):
   - OpenRouter (`/api/v1/models?output_modalities=all`, `/api/v1/images/models`, `/api/v1/videos/models`): modalities, limits, token, image, and video prices, voices, format choices
   - LiteLLM (`model_prices_and_context_window.json`): each provider's own entries, token prices, and per-image, per-second, and per-character media prices
3. Local Endpoint Probes ($0 Priority):
   - Ollama (`/api/tags` + `/api/show`)
   - llama.cpp server (`/v1/models` + `/props`)
   - ComfyUI (`/object_info`)
4. User Overrides: Explicit per-model aliases, custom pricing (`MoneyMicros`), context limits, and endpoint overrides stored locally in SQLite.

## 2. Deterministic Merge Precedence
`User Override > Local Endpoint Probe > Live Provider /models > Upstream Aggregator > Signed Baseline Pack`.
All merged pricing is normalized into exact integer `MoneyMicros(i64)` per 1M tokens (or per media unit) at ingest time; invalid/NaN values are rejected.

## 3. Default Models
Settings > Default models holds one app-wide choice for chats and one per background task (`UtilitySlot` in `crates/bistre-core/src/utility.rs`: chat titles, summaries, translations); each task follows the chat default until the user sets its own, and side questions always use the chat's model. A chat or its assistant can set its own model, which wins (Model resolution order below). Picture, speech, and video models answer a chat turn as the chat's model (Spec 02 Media), so they need no separate setting. When Settings > Safety & Budget > Prefer free local models is on, a background task that follows the default runs on an enabled local provider instead (Spec 06).

## Live Model Catalog (`registry.rs`, `registry_parse.rs`)
- Zero hardcoded model facts: a single-flight, detached background sync reads four public lists in order: OpenRouter `GET /api/v1/models?output_modalities=all` (the bare list holds text models only), OpenRouter `GET /api/v1/images/models` (picture shapes and sizes from `supported_parameters.aspect_ratio|resolution.values`; it has no prices, so a model that also writes text takes only its choices from it), OpenRouter `GET /api/v1/videos/models` (video `pricing_skus` and `supported_durations`), and LiteLLM `model_prices_and_context_window.json`. Earlier sources win per field; later ones fill gaps. Vercel AI Gateway and models.dev are not read: models.dev holds per-token costs only, and both repeat what these two carry.
- Fields per model (`ModelRates`): token prices (`prompt|completion`, `input_cost_per_token|output_cost_per_token`), cache read and write rates (5-minute and 1-hour), context window (`context_length`, `max_input_tokens`, else `max_tokens`; 0 means unreported), reply limit (`top_provider.max_completion_tokens`, `max_output_tokens`), reasoning (`supported_parameters` has `reasoning`, `supports_reasoning`), input and output modalities (`architecture.*_modalities`; LiteLLM `supported_modalities`, `supported_output_modalities`, else `mode` and the `supports_vision|audio_input|audio_output|pdf_input` flags; `speech` is audio), per-image price (`output_cost_per_image`), per-second video price (the dearest of LiteLLM `output_cost_per_second*` and OpenRouter `pricing_skus` keys naming a second, `cents_` keys in cents), the longest video (`supported_durations`), the per-character speech price (`input_cost_per_character`), and, kept apart as `ModelExtras`, the first voice (`supported_voices`) and the format choices: picture shapes (`w:h` with plain decimals such as `9:19.5`; `auto` and anything else dropped), sizes (`1K`, `720p`), and video lengths (`supported_aspect_ratios`, `supported_resolutions`, positive `supported_durations`; `-1` means the model decides), each in source order, once, at most `MAX_MEDIA_CHOICES` (32). FFI `lookup_model_catalog_info` reports them with `writes_text`, so the composer shows Thinking, Format, or both by what the model does (Spec 08).
- A model that writes text needs both token prices to be priced; a model that writes no text may have none (it is billed per image, second, or character).
- Lookups are scoped to the serving provider (`CatalogScope`): its namespace comes first (`openrouter` for its host, `gemini` for the Gemini dialect, else the second-to-last label of the API host, matched to a LiteLLM `litellm_provider` exactly or as `<label>_...`), then the plain id, then the maker's id without its `vendor/` prefix (from OpenRouter, whose ids are `maker/model` at the maker's price, and from unprefixed LiteLLM ids, the makers' own APIs), then any source's entry by that id as the last resort. Each later match only fills fields the earlier one lacked. A reseller's prefixed entry (`azure/eu/gpt-x`) never prices the maker's `gpt-x`, and OpenRouter's moving `~vendor/x` aliases never claim a bare id. On the live lists, 204 of 205 native OpenAI, Anthropic, and Gemini chat models get the maker's price and window (191 and 173 before). Tests: `registry::tests::{a_resellers_entry_never_prices_the_makers_model, the_serving_provider_prices_its_own_models, media_models_carry_their_modalities_and_units}`.
- Within one refresh earlier sources win and later ones fill gaps; the refresh as a whole replaces the prices known before it, and ids no source returned this time keep their old price (`RateTable::refreshed_from`, test `a_refresh_replaces_known_prices`); each source publishes incrementally via `tokio::sync::watch`. Freshness TTL 24 h (`REGISTRY_TTL`), empty-sync cooldown 60 s, at most a 2.5 s wait for one model's rate (`REGISTRY_MODEL_WAIT`; the download is never cancelled), once per run: the run's first lookup waits, and each step's reservation and cost, and each helper call, read the newest table without waiting, so an unpriced model never stalls a reply more than once.
- Prices convert once, with integer decimal parsing only, to `MoneyMicros` per 1M tokens or characters, per image, or per second (JSON floats are re-read from their shortest decimal text, never multiplied as `f64`). Unknown models are `cost_known: false` (never a guessed rate); loopback providers are always `$0`.
- Catalog GETs run through `PublicWebTransport` and carry no identifiers.
- Settings > Providers > a model > Fill from catalog reads the same scoped entry (`lookup_model_catalog_info(provider_id, model_id)`) and fills the limits, token prices, and the cache read and both cache-write rates, written out exactly (0.075, never a rounded 0.07; `microsAsDollars`). A model that writes no text fills no token prices.

## Pricing Refresh Policy
- Public lists (`PRICING_SOURCES`) are fetched at most once per 24 h: at engine start when `AppSettings.pricing_auto_refresh` is on (default), or when the user presses Update prices now (Settings → Safety & Budget). A run never starts a fetch.
- The merged table, its voices and format choices, and the namespace list are cached in `<data_dir>/pricing_cache.json` with `PRICE_CACHE_FORMAT` (8); a cache from another format version is ignored and rebuilt, and a fresh cache counts as the last successful sync. Writes are atomic (temp → `sync_all` → rename).
- With automatic updates off and no cache, unknown prices show the quiet "price unavailable" info; while a spending cap is active such a request is blocked until the user allows it once (Spec 06 "Unknown prices").
- `EngineClient::model_context_tokens(provider_id, model)` serves the composer ring: a saved per-model override, else the scoped catalog window.

## Model resolution order
- A run's provider and model come from, in order: the chat's own (a provider pinned by the chat or its assistant must be usable or the run fails), the assistant's default, Settings > Default models, the model last picked in Settings > Providers, then the provider's default model. The chat's model picker sets the open chat's own model, so the Default-models setting stays the default for every other chat. The context breakdown resolves the model in the same order. Tests: `egress_tests::the_default_model_setting_wins_over_the_last_pick`, `apps/bistre_app/test/picker_sets_chat_model_test.dart`.
- Background utility slots (`crates/bistre-core/src/utility.rs`): Settings > Default models routes chat titles (`generate_thread_title`, also auto-run after a new chat's first reply unless the user already renamed it), model-written compaction summaries (`compact_thread` when no manual summary is supplied, falling back to the local extractive summary offline), and message translations (`translate_node`, committed as a new sibling version on the same parent). Every background request runs with `store: false`, honours provider advanced options, reserves and settles spend through Wallet Shield, and prefers an enabled loopback local provider when Settings > Safety & Budget > Prefer free local models (`wallet_local_first`) is on and the slot follows the global default. Tests: `egress_tests::{default_models_title_slot_generates_and_sanitizes_thread_title, default_models_summary_slot_writes_compaction_summary, default_models_translate_adds_sibling_version_in_target_language, wallet_local_first_routes_background_tasks_to_local_provider}`, `apps/bistre_app/test/default_models_and_inspector_test.dart`. The built-in title, summary, and translation prompts live only in `utility.rs`; the app shows the title prompt through FFI `default_title_prompt` and stores an empty setting while it is unchanged, and an empty setting or a stored copy of the earlier built-in title prompt sends the current one. Tests: `built_in_prompts_follow_the_prompt_rules`, `a_stored_copy_of_the_old_title_prompt_sends_the_built_in_one`. A side question (`/btw`, `ask_side_question`, `UtilitySlot::SideQuestion`) runs on the chat's own provider and model with the latest messages of the active branch (at most 24,000 characters) and the question (at most 4,000), and its answer is shown beside the chat and never saved to it. Summarize into a new chat runs the Summary slot and fails when the summary does, never falling back to an empty chat. A drafted message (`/draft`, `draft_next_message`) uses the side question's model and transcript with an optional note (at most 2,000 characters) and returns at most 8,000 characters for the composer, never saved to the chat. A guided Regenerate (`/guide`, `regenerate_reply_guided`) adds the direction (at most 2,000 characters) to that reply's instructions only.
