# Spec 00: System Architecture & Execution Topology

## 1. Layer Boundaries
Bistre enforces strict one-way hexagonal dependencies (`ADR-0001`, `ADR-0003`):
- Thin Flutter UI (`apps/bistre_app`): Rendering, runtime ICU localization, accessibility, keyboard focus, and minimal platform shims (`WindowCompat.setDecorFitsSystemWindows`, run-scoped FGS, and the `dev.bistre.app/vault_key` Android Keystore channel that only carries the opaque vault data key into `init_runtime`, ADR-0010). Zero HTTP, SQL, LLM prompt logic, or UI kit dependencies.
- Thin FFI Bridge (`crates/bistre-ffi`): FRB 2.13.0 DTO translation, runtime initialization (re-initialising shuts the previous engine down first, so there is never a second SQLite writer), and 16ms coalescing `StreamSink` event forwarding. Zero business logic. Engine shutdown cancels runs and waits up to 5 s for them (a `JoinSet`) before closing storage.
- Pure Rust Domain Core (`crates/bistre-core`): Owns `EngineClient`, canonical DAG orchestration, providers, self-healing, AIO registry, in-process tools, MCP, lorebooks, trust/wallet shields, and OTA verification planning. Zero Flutter/FFI/GUI knowledge.
- Core Network & Policy Modules (`ADR-0017`): `providers::dispatch` (single provider path with key rotation, heal ladder, typed retry hints), `sse` (`SseFramer`), `ssrf` (`PublicWebTransport`), `registry` (live pricing), `credentials`, `error_policy`, `approval` (one-use tool permits), `import_policy`, and `process_util` (the only child-process constructor).
- Storage & Crypto (`crates/bistre-storage`, `crates/bistre-crypto`): SQLite WAL single-writer actor + FTS5; `minisign-verify` offline verification + `SecretVault` trait.
- Desktop Services (`crates/bistre-daemon`, `crates/bistre-updater`): Resident local background daemon (tray, UDS/Named Pipe IPC, Remote Bridge mTLS server) and side-by-side crash-loop rollback updater.

## 2. One Brain, Any Body (`EngineClient` Trait)
`crates/bistre-core/src/engine_client.rs` defines the async `EngineClient` trait with three interchangeable backends behind one FRB contract:
1. `InProcessEngine`: Embedded directly inside the process (Android production and standalone desktop).
2. `LocalIpcEngine`: Connects thin Flutter GUI over Unix Domain Socket (`$XDG_RUNTIME_DIR/bistre-daemon-<16 hex of the data dir>.sock`) or Windows Named Pipe (`\\.\pipe\bistre-daemon-<16 hex of the data dir>`) to active-scoped `bistre-daemon` (`ADR-0013`). The endpoint name is predictable, so the channel is bound to the signed-in user: the daemon creates every pipe instance with an owner-only protected DACL (current user + `SYSTEM`, `bistre_crypto::pipe_identity::OwnerOnlyPipeSecurity`) and rejects remote clients, and the client refuses any pipe whose server process runs as another account (`GetNamedPipeServerProcessId` + token user SID) or any Unix socket whose peer uid differs, before writing a request (`diag.daemon.unavailable` / `ipc_server_foreign_user`). The audited Win32 shims live in `bistre-crypto` (`windows-sys` features `Win32_Security_Authorization`, `Win32_System_Pipes`). Closing the Flutter window terminates the GUI process completely (0 MB Impeller/Dart RAM) while `bistre-daemon` stays alive strictly while an agent run or scheduled cron task is active (≤30 MB RSS), exiting cleanly once idle. On Windows and Linux the app uses the folder's daemon, starts it detached when none answers, and runs the engine in-process only when no daemon is installed; one process ever writes a folder (`daemon.lock`). Every `EngineClient` method crosses the pipe through one generated RPC table, and events arrive on one subscription that replays the event log after a reconnect (`ADR-0003`).
3. `RemoteBridgeEngine`: Connects mobile/desktop UI over TLS 1.3 mTLS WebSocket to a QR-paired remote `bistre-daemon` over LAN/Tailscale.

## 3. Process, Thread & Shutdown Ownership
- Every background task runs on a bounded Tokio runtime or dedicated named OS thread (`bistre-sqlite-writer`).
- Channels are strictly bounded (`cap=256`); contiguous token deltas merge under backpressure so memory never grows unboundedly.
- Graceful shutdown (desktop window close through `didRequestAppExit`, Android `detached`; `FolioController.shutdownEngine` runs once) flushes pending chat deletes, window bounds, and quiet settings, then calls `shutdown_runtime`: runs are cancelled and every run's `wake` is notified, so runs in a backoff or approval wait record their final state instead of being aborted at the 5 s drain deadline. It then runs `reclaim_storage()` (`PRAGMA wal_checkpoint(TRUNCATE)` + `PRAGMA optimize`), and releases the data folder's writer lock (`daemon.lock`). With the daemon, `shutdown_runtime` only ends the app's event subscription: the daemon finishes live work and exits once idle.

## 4. Phased Rollout Waves (Day-1 Abstractions)
All AIO, performance, i18n, and two-track OTA abstractions are locked from Day 1 while features ship vertically in three waves:
- Phase 1 (Core Desktop & Android Client, self-updatable from Day 1): Core workspace (`bistre_app`, `bistre-core`, `bistre-storage`, `bistre-crypto`, `bistre-daemon`, `bistre-updater`), Big 3 + OpenAI-compatible wire dialects, 5-class self-healing, synthesized AIO registry + Default models, in-process Rust tools + MCP (`2026-07-28` + legacy fallback), worktree sub-agents, Lorebooks & `SKILL.md` loader, Dual Trust + Wallet Shield, and QR-paired mTLS Remote Bridge.
- Wave 2 (Voice & Image AIO): Speech-to-Text, streaming Text-to-Speech, and schema-driven OpenAPI async image generation/editing with WAL-before-POST idempotency.
- Wave 3 (Video & Fireside Full-Duplex): Async video generation/editing/dubbing and Fireside full-duplex voice (Android BLE Audio + Oboe + AEC3 + Silero VAD).
