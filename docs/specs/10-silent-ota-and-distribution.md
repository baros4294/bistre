# Spec 10: Silent Two-Track OTA Updates & Direct GitHub Distribution

## 1. Cryptographic Trust & Zero-Telemetry Feed
All updates are 100% open-source, self-hostable (configurable feed URL, default GitHub Releases), and zero-telemetry (plain HTTPS GET of static `manifest.json` + `manifest.json.minisig`, zero device identifiers).
- Every manifest and artifact is verified offline via `bistre-crypto` (`minisign-verify 0.3.0`, pinned Ed25519 public key) plus SHA-256 digest match and monotonic anti-rollback version floor before staging.
- Fail closed: if the release key is empty `check_for_updates` returns `diag.ota.signing_key_missing` before any request; the `.minisig` is mandatory. The official Ed25519 release public key (`84A60109283936B3`, `RWSzNjkoCQGmhPhmWgUEVRju0AEHELP3evLMpoKRKRvhlpCZAL43T2Yb`) is embedded in `OFFICIAL_RELEASE_PUBKEY_B64`. A successful check yields a core-held `VerifiedManifest` (private fields, built only after the signature verifies); `stage_update` stages only that manifest, so a URL, digest, or version forged by the UI is rejected (`ota_manifest_unverified`). Tests: `crates/bistre-core/src/ota.rs` (`missing_release_key_disables_ota_before_any_request`, `official_release_pubkey_verifies_minisign_012_signature_and_rejects_tampering`, `tampered_or_unsigned_manifest_is_rejected`) and `crates/bistre-core/src/tests.rs`.
- Release workflows additionally emit GitHub Sigstore build provenance attestations (`actions/attest-build-provenance`) and one CycloneDX SBOM per shipped Rust binary (`cargo-cyclonedx 0.5.10`): `-engine.cdx.json` (`bistre-ffi`) and `-daemon.cdx.json` are rejected below 50 libraries, `-updater.cdx.json` below 10.
- Release builds: the Linux release builds inside a digest-pinned `ubuntu:20.04` container (glibc 2.31; `install-rust.sh` bootstraps a checksum-pinned `rustup-init` there), and packaging refuses any staged ELF file that needs a `GLIBC_` symbol above 2.31, the floor the `.deb` declares. `SOURCE_DATE_EPOCH` is the tagged commit's time; the daemon and updater build with `--remap-path-prefix` so runner paths stay out of them; the app's engine library builds through the Flutter hook with `--locked` like every other Cargo command. The Dart symbols split out of the APK (`--split-debug-info`) are kept as the run artifact `symbols-android-arm64` (90 days, never published). Release jobs restore no caches. `packaging-smoke` (required before publishing) installs the `.deb` on a clean runner, checks the daemon health and that the app is still running after 15 s under `xvfb`, removes the package and checks nothing is left, starts the AppImage the same way, reads the `.rpm`'s name and files, and on Windows installs `setup.exe` silently per user, checks the daemon and a 15 s app start, then uninstalls and checks the files are gone. Open: byte-for-byte reproducibility is not checked, Rust native symbols are stripped (`strip = "symbols"`), and the container build and `packaging-smoke` first run in the release dry run `[UNVERIFIED]`.
- Windows release smoke check: the tagged release verifies `bistre_app.exe` `ProductVersion` equals the tag, `ProductName` is `Bistre` (`apps/bistre_app/windows/runner/runner.rc` carries real product metadata and takes its version only from the Flutter build's `FLUTTER_VERSION`, that is `apps/bistre_app/pubspec.yaml`; it fails to compile without it), and `shell32!ExtractIconExW` finds an embedded icon.
- Supply-chain workflows: `.github/workflows/codeql.yml` (path-selected `rust` + `actions`, weekly), `.github/workflows/scorecard.yml` (top-level `permissions: {}`, SARIF upload), and zero-checkout `.github/workflows/dependabot-automerge.yml` (merges only minor/patch Dependabot PRs after CI succeeded on the exact head SHA via `gh pr merge --rebase --match-head-commit`, then dispatches `ci.yml` on `main`, because a push made with `GITHUB_TOKEN` starts no workflow while `workflow_dispatch` always does; Dependabot cooldown stays 7/14 days).
- CI build reuse: `flutter-desktop` builds and smoke-tests `bistre-daemon` + `bistre-updater` once per OS and its launch checks reuse them (`rust-fortress` no longer builds them; any Rust change also plans `flutter-desktop`). `android-arm64-16kb` restores the pinned NDK with `actions/cache/restore` and saves it from `main` only; `provision-android-sdk.sh` reinstalls it unless the restored copy is complete.
- Workflow lint: every workflow passes `zizmor --persona auditor` (the CI setting) and `actionlint` (with `zizmor 1.33.1` offline and `actionlint 1.7.12` via `uvx`). Every job has an explicit `name` equal to its check context (matrix values appended as GitHub does by default), every permission beyond `contents: read` carries an explanatory comment, and Rust toolchains install through a `rustup toolchain install "$RUST_VERSION" --profile minimal` script step instead of a third-party toolchain action.
- Android release signing: `release.yml` `build-android` has no secrets and no `release` environment; it builds a debug-signed intermediate (`BISTRE_ALLOW_DEBUG_SIGNING=1`, the only way Gradle lets a CI release build skip the release keystore) and uploads it as `unsigned-android-arm64` (never matched by the publish job's `bistre-*` download). `sign-android` (`release` environment) is the only job that sees the keystore: it fails when any of `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` is empty, decodes the keystore into `$RUNNER_TEMP` with 0600 and removes it on exit, re-signs with `apksigner`, and refuses to continue unless `apksigner verify --print-certs` shows exactly one signer whose certificate SHA-256 equals the pinned `ANDROID_RELEASE_CERT_SHA256`, then attests and uploads `bistre-android-arm64`. `ci.yml` check builds set `BISTRE_ALLOW_DEBUG_SIGNING=1` explicitly. `[UNVERIFIED]` until the release dry run: that `apksigner sign` replaces the intermediate's debug signature (the one-signer check fails closed if it does not).
- Windows builds are unsigned (no Authenticode certificate). SmartScreen may warn on first run; integrity comes from the SHA-256 sums and Sigstore build-provenance attestations published with each release.

## 2. Track A: Zero-Restart Signed Data Packs (All Platforms)
Covers non-executable JSON/binary data only: AIO model catalog snapshots, hot-loadable ICU locale packs, and built-in tool/media OpenAPI schemas.
- Verified atomically via `bistre-core::verify_data_pack` and activated immediately in memory with zero restart.

## 3. Track B: Frictionless Native Binary Updates (Direct GitHub Distribution)
- Windows (`bistre-updater`): Side-by-side layout under `%LocalAppData%\Bistre\versions\<semver>\` fronted by a static launcher (`bistre-launcher.exe`). Never overwrites running `.exe`/`.dll` files or Start Menu `.lnk` shortcuts. Stages verified new version in background; swaps pointer only when `active_runs == 0` (on next idle relaunch or user-accepted restart).
- Linux: Self-managed `.AppImage` updates atomically via `.AppImage.new` → `rename()`. Automatically disables binary self-update when `FLATPAK_ID`, `SNAP`, or read-only `/usr`/`/opt` package-manager ownership is detected (`detect_update_ownership`), displaying a passive package-manager update notice instead.
- Android (Direct GitHub APK Only): Single `arm64-v8a` 16KB-aligned APK published directly on GitHub Releases (`REQUEST_INSTALL_PACKAGES` in `src/main/AndroidManifest.xml`, `PackageInstaller` session API, Ed25519 manifest verification, and pinned APK signing-cert SHA-256 check; Play Store and F-Droid store flavors removed).

## 4. Active-Run Drain, Expand-Contract DB Safety, UI Surface & 3-Boot Rollback
- End-User OTA Controls (`crates/bistre-core/src/ota.rs` + `Updates & Storage` Settings view): `check_for_updates` fetches the user's configured `manifest.json` + `.minisig`, verifies offline Ed25519 signature + semver floor + release channel (`stable` skips prerelease tags; `beta` accepts prereleases), surfaces release notes and an Ed25519 verified badge inside `Settings → Updates & Storage` (an error shows there in plain words, its code behind Technical details, never in the chat composer; a failed download from the top banner offers Open Updates; the feed field notes that a browser downloads `manifest.json` instead of showing it), and stages verified downloads via `stage_update` into `<data_dir>/ota_staging/` with SHA-256 verification and an atomic `staged.json` receipt. `AppSettings.ota_auto_check` controls the quiet launch update check (exposed as a toggle in Updates settings). When already on the latest version (`latest == current`), `reinstall_update` allows explicitly re-staging the exact running version while strictly keeping downgrade protection against older versions.
- Track B never interrupts active LLM streams, agent tasks, or media jobs (`active_runs > 0` flags `active_runs_blocking` and defers swap until idle).
- Expand-Contract SQLite migrations guarantee `N-1` binary compatibility with `N` schema + `.pre-vN.bak` safety copies.
- `LauncherWatchdogState` (`crates/bistre-updater`) tracks `pending_boot_attempts`; `bistre-updater --apply-staged <data_dir> <install_root>` re-verifies the staged payload's SHA-256 against `staged.json` (refusing externally managed Flatpak/Snap/system installs), stages it into `<install_root>/versions/<version>/`, and updates `launcher-state.json` atomically; `--mark-healthy <install_root>` records a healthy boot. If the new binary fails to signal `mark_boot_healthy()` within 15s across 3 consecutive launches (`MAX_CRASH_BOOTS = 3`), the launcher automatically reverts `active_version` to `last_healthy_version`.

## 5. Payload Integrity (`crates/bistre-core/src/ota.rs`)
- Feeds, signatures, and payloads require `https://` (plain `http://` only for loopback test feeds, decided by the parsed host via `net::is_loopback_url`, never a string prefix, so `http://localhost.evil.com` is refused); manifests and signatures are read with a 1 MiB cap. OTA traffic uses its own credential-free `http_clients::ota_client`, which follows at most 6 redirects, each to `https` or a loopback host (the provider client follows none).
- Only a strictly newer SemVer than the running `CORE_VERSION` is ever staged (`ota_not_newer`), so a replayed older or equal signed manifest can never downgrade (test `ota::tests::staging_refuses_a_version_that_is_not_newer`).
- Manifest v2 (`crates/bistre-core/src/ota_manifest.rs`): `{"format": 2, "semver", "track", "release_notes", "targets": {"windows-x64" | "linux-x64" | "android-arm64": {"url", "sha256", "size_bytes"}}}`, `deny_unknown_fields`; `sha256` is a `Sha256Hex` (only 64 hex characters), `size_bytes` is non-zero. Each target lists the file that build installs: the Windows `-setup.exe`, the Linux `.AppImage` (`.deb`/`.rpm` stay with the system package manager, the portable `.tar.gz` and the SBOM are never assets), and the Android `.apk`. `OtaTarget::current()` picks the running build's asset. Another `format` is `diag.ota.manifest_unsupported` (a v0.1.2 install reinstalls once from GitHub Releases, as decided); a release without this platform is `diag.ota.no_asset_for_platform`. The release tool `crates/bistre-core/examples/ota_manifest.rs` writes the manifest with the same types (`build`, which refuses a tag other than the version compiled into core, `CORE_VERSION` from `Cargo.toml`: an installed build reporting an older version than its manifest would be offered the same update after every install) and checks it before publishing (`verify`: signature, the app's own parser, every target, each file's digest and size; fails closed). Tests: `ota_manifest::tests`, `ota::tests::old_or_incomplete_manifests_fail_with_their_own_reason` (fixtures signed with a throwaway test key).
- A payload without a SHA-256 is never staged (`DiagnosticKey::OtaIntegrityFailed`). Downloads stream chunk by chunk into `bistre_crypto::Sha256Stream` and a `.partial` file with a hard 256 MiB cap (also checked against `Content-Length` and the manifest size); only a verified payload is renamed into place, and an unverified partial file is deleted.
- Version precedence follows SemVer 2.0 including prereleases (`1.0.0 > 1.0.0-rc.10 > 1.0.0-rc.2`; build metadata ignored).

## Release Pipeline
- `.github/workflows/release.yml` first runs `ci.yml` unchanged (`workflow_call`), so a tag ships only after the same gates as a pull request, including the release-build launch and Spec 11 budgets.
- Android release artifacts enforce the same 32 MiB APK and 10 MiB `libbistre_ffi.so` budgets as CI.
- Release packages:
  - Windows (`packaging/windows/bistre.iss`): per-user Inno Setup 6 installer (`bistre-v<semver>-windows-x64-setup.exe`, installs to `%LocalAppData%\Programs\Bistre` with zero UAC prompt so `%LocalAppData%\Bistre` user data stays isolated) plus portable `bistre-v<semver>-windows-x64.zip`.
  - Linux (`packaging/linux/build-packages.sh`): universal `bistre-v<semver>-linux-x64.AppImage` (via checksum-pinned `appimagetool 1.9.1`), Debian/Ubuntu `bistre-v<semver>-linux-x64.deb` (`/opt/bistre`), Fedora/RHEL/openSUSE `bistre-v<semver>-linux-x64.rpm` (`/opt/bistre`), plus portable `bistre-v<semver>-linux-x64.tar.gz`.
  - Android: `bistre-v<semver>-android-arm64.apk` (16 KB aligned minified).
- `sign-and-publish` (tags only, `release` environment with required reviewers) downloads only the `bistre-*` artifacts (never the `ci` job's debug bundles), builds `manifest.json` v2 with `cargo run -p bistre-core --example ota_manifest -- build` (pinned `releases/download/<tag>/<file>` URLs), signs it with `minisign 0.12` (checksum-pinned) using `MINISIGN_SECRET_KEY` / `MINISIGN_PASSWORD`, runs `ota_manifest -- verify` against the embedded release key (fail closed), and creates the GitHub Release. Without the secret the job fails: there are no unsigned releases. The official Ed25519 release keypair (key id `84A60109283936B3`, public key `RWSzNjkoCQGmhPhmWgUEVRju0AEHELP3evLMpoKRKRvhlpCZAL43T2Yb`) is provisioned: public key embedded in `OFFICIAL_RELEASE_PUBKEY_B64` (`crates/bistre-core/src/ota.rs`) and encrypted secret key + passphrase stored in the GitHub Actions `release` environment.
