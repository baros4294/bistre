# Spec 11: Performance, Memory, Battery & Binary Budgets

## 1. Measurable Invariants & CI Guardrails
| Metric | Budget | Hard Fail | Enforcement |
|---|---|---|---|

## 2. Structural Efficiency Techniques
- FFI Delta Coalescing: `crates/bistre-ffi` batches high-frequency streaming deltas on a 16ms cadence over bounded channels (`cap=256`), preventing Dart isolate thrashing. The core already coalesces each run's text into at most one `DeltaBatch` per 16 ms frame before the `broadcast(256)` bus (`engine_runs::DELTA_FRAME`), so a fast stream cannot overrun it; if a subscriber still lags, FFI sends `events_lagged` and the app reloads state from storage instead of showing an error. Unknown event kinds from a newer core are ignored.
- Core delta frames: the run loop coalesces text and thinking deltas into at most one event each per 16 ms frame, flushed by a frame ticker beside the stream, so the last text of a burst is shown within a frame even when the provider then pauses (it used to wait for the next chunk, up to the 90 s idle timeout). Test: `egress_tests::the_last_text_before_a_pause_is_shown_at_once`.
- Less work per frame and per step: each SSE frame is JSON-parsed once and every reader (terminal check, usage, text, thinking, structured frames, grounding, finish) works on that value (it was parsed about six times; behaviour is covered by the existing parser tests); token counts of texts of 1 KiB or more are cached by content hash (blake3; bounded at 8,192 entries; test `tokenizer::tests::a_long_text_is_counted_once`), so the branch re-counted every step costs one BPE pass per text; a step reads only its own branch through a bounded recursive SQLite walk (`StorageHandle::list_branch`, test `the_branch_walk_returns_only_the_leafs_ancestry`), not every node of the thread.
- No work on the keystroke or resize path: the `@` menu reads the workspace once per root, asynchronously, when it opens (`loadWorkspaceEntries`; it used `listSync` on every keystroke, which froze the window on Windows); window bounds join the debounced quiet settings save (one write after the window settles, always with the latest settings, so a change made meanwhile is never undone; saved at once when the app is paused). Tests: `mention_menu_test.dart`, `window_bounds_test.dart`.
- Windowed chat history: a chat opens on its newest `kFeedPage` (400) messages (`folio_controller_paging.dart`); chats up to that size load whole as before. Older pages load from the Show earlier messages button at the top of the feed (the first message shown stays in view), and automatically when something needs an unloaded message: a search hit or reveal, a pinned message, or the session tree (which loads the whole chat). Pages come from core's `list_nodes_window(thread_id, before_node_id, limit <= 500)`, which pages by write order, so messages sharing a timestamp are never skipped; one extra row tells whether older messages exist. A reload after a change keeps as many messages as are shown. The first loaded messages, whose parents are on an unloaded page, start the visible branch on the way to the newest message and show no version switcher; a partly loaded chat's cost comes from core's `thread_spend_micros` (the wallet ledger) instead of the loaded replies. Tests: `feed_paging_test.dart` (desktop, phone at 200 % text, Arabic RTL), storage `list_nodes_window_paginates_chronologically_and_tracks_history_rev`.
- Slim node metadata: the FFI node DTO carries the metadata without its opaque replay payload (reasoning blocks and signatures, server chain state, origin, and grounding and attachments, which arrive typed), so loading a thread no longer copies large encrypted reasoning into Dart; each node's usage is parsed once and cached (`EngineNode.usageMeta`). Test: `replay_policy::tests::the_app_gets_slim_node_metadata`. A finished run reloads the shown window in one `list_nodes_window` query: 401 messages of 2 KiB each read in about 3 ms (release build, measured on the development laptop). Reloading only what changed would need an update counter on every node write (edits, usage, deletes), so it is not built; `thread_history_rev` serves the new-reply mark (Spec 08).
- UI caches sized and reused: the Markdown parse cache is bounded by the text it holds (4 Mi characters) as well as 256 entries, and a growing reply replaces its previous frame instead of adding a near-copy (it left up to 256); the tool timeline folds its rows once per change of its entry list, not every frame of the live reply; branch info for every message comes from one children-by-parent index built once per node list (it was rebuilt for each message, O(n²) per build). Tests: `markdown_cache_test.dart`, `tool_timeline_fold_test.dart`, `branch_index_test.dart`.
- Bounded images and lists: an attachment preview decodes at most 2560 px on its long side (`ResizeImage`, fit policy; a 48 MP photo decoded in full is about 190 MB) and provider icons decode at their drawn size; model lists are built lazily with no cap (they stopped at 60). Tests: `image_preview_test.dart`, `model_list_test.dart`.
- Streaming checkpoints: the partial reply is checkpointed append-only (`append_agent_run_partial_text`) at most every 250 ms and only after 4 KiB of new text, plus once at the end.
- Storage readers, no pool: each read opens a read-only connection and drops it at once (measured `~56 µs` per open, ~1.1 ms for `list_threads` over 300 chats in release builds).
- Chat history, not paged: `list_nodes` for a 2,000-message chat (~2 MB) completes in ~8 ms in release core off the async workers, and the feed is already virtualized. Paging (`list_nodes_page` plus a center-sliver scroll anchor) is deferred until a measured thread switch exceeds ~100 ms.
- Long storage calls off the async workers: export, backup, full-text search, and loading a chat's history run through `off_worker` (`crates/bistre-core/src/off_worker.rs`, Tokio's blocking pool), so a reply streaming on the same worker never waits behind them. Sub-millisecond lookups stay inline.
- A backup never holds the writer: `VACUUM INTO` runs on its own read-only connection (a consistent WAL snapshot; `query_only` stays off because it refuses the write to the new file), so runs keep saving during a large backup. Test: `a_backup_does_not_wait_for_the_writer`.
- File tools off the async workers: `read`, `edit`, `grep`, and `glob` run through `off_worker::blocking`; tool outputs over 64 KiB are spilled on the blocking pool with an atomic temp file, `sync_all`, and rename. Test: `a_large_tool_output_is_saved_whole_without_leftover_temp_files`.
- No lock across an await: `clippy::await_holding_lock` and `await_holding_refcell_ref` are denied explicitly in `[workspace.lints.clippy]`.
- Zero-Fork Native Tools: File read, ripgrep search, glob, hash-anchored edit, and diff execute in-process inside Rust with zero subprocess spawn overhead.
- Asset & Binary Hygiene: Bundled static weights only (`Inter`, `JetBrainsMono`, `NotoSansMath`, enforced ≤ 2.0 MiB total by `bistre_guard`), pre-compiled `.vec` vector icons (`vector_graphics`), universal single-vocabulary `tiktoken` (`vocab-o200k_base` only; zero hardcoded model/vendor vocabs), Rust `lto = "thin"`, `codegen-units = 1`, `panic = "abort"`, `strip = "symbols"`, `bistre-ffi` built as `cdylib` only, Android size profile overrides (`opt-level = "z"`, `lto = "fat"` via `hook/build.dart`), `Cargo.lock` dependency-count budget (≤ 380 locked crates enforced by `bistre_guard`), Android R8 (`isMinifyEnabled = true`, `isShrinkResources = true`), and `arm64-v8a` ABI split with `0x4000` (16KB) ELF alignment.
- VSync-Locked UI, Zero-Copy Streaming & Parallel Boot: `LiveTurnNotifier` schedules all paced and low-memory (33 ms) redraws via `SchedulerBinding.instance.scheduleFrameCallback` (zero raw `Timer`); `SmoothScrollController` uses critically damped `ScrollSpringSimulation` via `BallisticScrollActivity` preserving momentum across rapid wheel ticks; `MarkdownFolioView` caches `_ParsedDoc` (`blocks`, `direction`, `hasMath`) and tracks incremental line counts in `O(1)`; `FolioSidebar` virtualizes Chat and Pinned tabs via `ListView.builder`; `BistreLocalizationController` lazy-loads non-English catalogs on demand with an `O(1)` static-string ICU fast path; `PaintingBinding.instance.imageCache` caps at 16 MiB (8 MiB in low-memory mode); `SseFramer` uses a zero-copy read cursor; startup defers pricing sync until a provider is configured and parallelizes `loadSettings`/`listProviders`/`listAssistants`/`listThreads` before hydrating non-Frame-1 metadata (`wallet`, `storageStats`, `agentRuns`, `powerGuard`).
- Zero Idle FGS & Daemon Drain: Android `BistreAgentService` (`specialUse`) and desktop `bistre-daemon` run strictly while `active_runs > 0` or a scheduled job is active and stop cleanly when idle (`ADR-0012`, `ADR-0013`). The daemon has no short polling timer: its housekeeping task sleeps until the next cron deadline (re-reading schedules at most every 300 s) and wakes early on engine events or an attach/detach RPC; an active-scoped daemon exits 10 s after the window detaches with no work. It runs on two Tokio workers, serves at most 16 concurrent IPC connections, backs off `50 ms → 2 s` on accept errors, and rejects malformed RPC params.

## 3. Reference Hardware & Low-Memory Mode
Every budget above is targeted for these hardware classes:

| Class | Device Profile | Role |
|---|---|---|
| Low-end Desktop | `2 cores, 4 GB RAM` (Windows / Linux) | Minimum supported desktop |
| Low-end Android | `API 29+ (minSdk), 2 cores, 2 GB RAM` | Minimum supported phone |
| Mid-range Desktop | `4 cores, 8 GB RAM` | Build, test, and storage-budget reference |
| Everyday Android | Current-generation `arm64-v8a` Android phone | On-device manual checks |

- Low-memory mode: When host RAM is < 4 GB (desktop) or Android `ActivityManager.isLowRamDevice()` is true, Bistre caps streaming redraw at `30 fps`, skips overlay drop shadows, decodes attachments at most 2560 px a side off the UI thread, and caps the Skia GPU resource cache at 32 MiB (48 MiB on normal hosts, via `SystemChannels.skia` `Skia.setResourceCacheMaxBytes`).
- Bundled fonts: All bundled OFL font files together stay ≤ 2.0 MB (OFL-compliant subsetting preserving Latin, Vietnamese, prose, code, and math coverage); `NotoSansMath` registers lazily on the first rendered math block.
- SQLite WAL: `PRAGMA journal_size_limit = 8388608` (8 MiB) + `wal_autocheckpoint = 1000`; tool outputs > 64 KiB spill to a blob column; `reclaim_storage()` runs `wal_checkpoint(TRUNCATE)` + `PRAGMA optimize` (Spec 01).

## 4. Workspace Build & Storage QC Budgets
Local build caches are budgeted like runtime memory (`ADR-0016`):

| Bucket | Budget | Enforcement |
|---|---|---|
| `target/` (all Cargo profiles) | ≤ 4.0 GiB | `just disk`, `just prune`, auto-prune after `locked` heavy runs |
| `apps/bistre_app/build/` | ≤ 1.0 GiB | `just disk` |
| `apps/bistre_app/.dart_tool/` | ≤ 512 MiB | `just disk` |
| `.bistre-local/` (ledger, lock, logs) | ≤ 128 MiB | `just disk`, `just prune` |
| Single verification `.log` | ≤ 2.0 MiB | `just prune` |

- Cargo profiles (`Cargo.toml`): `[profile.dev] debug = "line-tables-only"` and `[profile.dev.package."*"] opt-level = 2, debug = false`. Android release builds override `opt-level = "z"`, `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, and `strip = "symbols"` through `apps/bistre_app/hook/build.dart`.
- Cargo config (`.cargo/config.toml`): `[build] jobs = 4`; `[registry] global-min-publish-age = "3 days"`; Android `aarch64` rustflags `force-unwind-tables=no`, `--gc-sections`, `--icf=safe`, `-z max-page-size=16384` (mirrored by `apps/bistre_app/hook/build.dart`, which unifies `CARGO_TARGET_DIR` to `<repo>/target` for `Swatinem/rust-cache` sharing, activates `release-android` flags on Android, and passes SQLite `-Oz -fno-unwind-tables -fno-asynchronous-unwind-tables -DSQLITE_OMIT_LOAD_EXTENSION -DSQLITE_OMIT_DEPRECATED -DSQLITE_OMIT_UTF16 -DSQLITE_OMIT_TRACE -DSQLITE_OMIT_PROGRESS_CALLBACK -DSQLITE_OMIT_TCL_VARIABLE`).
- Surgical pruner (`tools/bistre_guard/lib/storage_qc.dart`, never `cargo clean`): keeps only the caches the next build reuses, `target/debug`, `target/tmp`, and the Android target `target/aarch64-linux-android`; deletes every other `target/` folder (release outputs, other target triples) and a stray root `build/`; keeps the newest incremental session per crate stem; removes superseded nested build units while skipping any unit holding a shared library; deletes verification logs > 2 MiB.
- Single-run lock & ledger (`tools/bistre_guard/lib/ledger.dart`): heavy recipes run through `bistre_guard locked …` holding `.bistre-local/verification/run.lock`; `just check-all` records an FNV-1a 64-bit file ledger so `just status` / `just affected` report and run only the checks touched files need.

## 5. Repeatable Performance Harness (`just perf`)
- Desktop (`tools/bistre_guard/lib/perf_runner.dart`): `bistre-daemon --seed-synthetic 300 --data-dir <scratch>` seeds 300 synthetic chats in a scratch temp directory (never user data); the release app is launched three times with `BISTRE_DATA_DIR=<scratch>` and `BISTRE_PERF_PROBE=<file>`, reporting `first_frame_ms`, `chat_ready_ms`, `chat_count`, `idle_frames`, frame timings (`build_p95_ms`, `raster_p95_ms`, `vsync_overhead_p95_ms`), and idle memory after 10 s. Medians of three runs are checked against budgets; missing binaries are reported as `SKIP`. Windows and Linux default to Impeller (`BISTRE_IMPELLER=off` selects Skia GLES). Known budget risk: the last recorded measurement on Intel Iris Xe had Skia far ahead (300-chat `chat_ready_ms` `81–93 ms` vs 329 ms with Impeller, `raster_p95_ms` 3.35 ms vs 346.34 ms, idle working set `197–201 MB` vs 271 MB); that run predates the change that stopped the sidebar re-laying out the chat per frame, and must be repeated with `just perf` on Windows before release [UNVERIFIED: not re-measured in this change]. If Impeller still breaks a budget, Impeller stays the default and the result is reported (owner decision).
- Long tool session (`apps/bistre_app/test/long_session_probe_test.dart`): 500 tool turns keep the chat's tool rows at most 200 with outputs at most 16 KiB and the Markdown cache within its size; once the run ends there is no scheduled frame and no running animation (zero idle polling). The OS-level RSS of such a session and streaming p99 come from `just perf --strict`.
- Streaming (`apps/bistre_app/test/perf/streaming_frame_probe_test.dart`): streams an ~87 KB code fence in 16 ms delta batches and reports UI-thread build + layout + paint + semantics p50/p95 with semantics off and on. Chunked 8-line code fences (`kCodeChunkLines`) plus the open-fence `_ParsedDoc` memo, incremental line counter, and relayout-boundary feed constraints cut debug-VM streaming p95 from 114.33 ms to ~10.8 ms (`p50 ~7.7 ms`).
- Android (`just perf --android`): `adb shell am start -W -S` (`TotalTime`) and `dumpsys meminfo` `TOTAL PSS` after 10 s on an installed APK.
- `just perf` exits non-zero only on a hard-fail budget; `OVER` lines are reported without failing. Never loosen a budget to make a failing measurement pass.

## 6. CI Wall-Clock & Cache Budgets
- `Swatinem/rust-cache` runs with `shared-key`, `save-if: ${{ github.ref == 'refs/heads/main' }}`, and `cache-bin: false` (PRs restore but never write cache; binaries are never cached).
- A path-based `plan` job lets docs-only PRs skip Rust, Flutter desktop, and Android builds while `security-and-hygiene` and `repo-guard-and-docs` always run; any `.github/` change runs everything.
- Dependency downloads (`flutter pub get`, `sdkmanager`, tool archives) run through `.github/scripts/with-download-retry.sh` (transport errors only, `10/20/30 s` backoff).
- Superseded PR runs cancel via `concurrency`; `main` runs never cancel.

## 7. Fonts & Low-Memory Probes
- Bundled fonts stay under 2.0 MB total (1.58 MB after OFL subsetting); `NotoSansMath` is registered lazily by `MathFontGate` on the first math block.
- Low-memory detection runs asynchronously after startup without blocking `bootstrap`.

## 8. CI Performance Enforcement
- `flutter-desktop (ubuntu-24.04)` builds the Linux release bundle and daemon, then runs `xvfb-run -a dart run tools/bistre_guard/bin/bistre_guard.dart perf --strict --rss-report-only`: the release binary must launch and emit its probe, and any hard-fail breach fails the job.
- Profile-mode streaming frames: Linux CI runs `flutter drive --profile` on `apps/bistre_app/integration_test/streaming_perf_test.dart` (~87 KB fence at `~120 tok/s`). UI-thread build `p99 > 16 ms` fails CI; baseline measured 10.18 ms build p99 (within 60 Hz budget).
- Desktop app-owned memory: Windows CI runs `bistre_guard perf --app-memory` against a profile build (≤ 60 MB budget, > 80 MB hard fail; measured ~21 MB Dart heap + external). Process working set is reported for visibility because GPU driver shaders and OS shared libraries dominate total working set across every Flutter desktop application.
