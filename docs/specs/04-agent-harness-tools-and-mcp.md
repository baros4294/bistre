# Spec 04: Native Agent Harness, In-Process Tools & MCP

## 1. Zero-Fork In-Process Rust Tools
Every core workspace tool runs in-process inside `crates/bistre-core` (zero shell fork overhead, deterministic cross-platform UTF-8 handling):
- `read`: Line-ranged UTF-8 file reader returning `blake3` line-range hashes (`LINE#HASH`) and enforcing binary/size guards.
- `grep`: Built directly on `grep-searcher 0.1.17` + `ignore` (ripgrep engine) honoring `.gitignore` with bounded match/byte caps.
- `glob`: Built on `globset` + `ignore`, returning deterministic mtime-sorted paths.
- `edit`: Capability-scoped via `cap-std 4.0.3` `Dir` (`openat2`/`O_NOFOLLOW` eliminating symlink/TOCTOU escapes), verifying exact `blake3` hash anchors prior to atomic temp-file + `rename` swap (with 3-step backoff on Windows AV `ERROR_SHARING_VIOLATION`) and persisting a pre-image snapshot for 1-tap rewind.
- `diff`: Unified structured diffs computed in-process via `imara-diff`.
- `fs_*` (`crates/bistre-core/src/fs_tools.rs`): `fs_list` (Tier-0; one folder level, folders first with a `/`, file sizes, secret files hidden, at most 500 entries), and the Tier-1 `fs_write` (whole file, up to 2 MiB), `fs_multi_edit` (up to 32 exact replacements applied all or none), `fs_move` (never replaces an existing file, same workspace folder only), and `fs_delete`. Every change saves a workspace checkpoint first, so the tool row's rewind restores it (rewinding a created file removes it only while it is unchanged). Overwriting or editing a file needs this run's fresh read of it (`diag.tool.stale_read`); `fs_delete` always asks, even when edits are allowed. Tests: `fs_tools::tests`, `approval_flow_tests::deleting_a_file_asks_even_when_edits_are_allowed`.
- `shell` (guarded): every child process (tools, hooks, git worktrees) is created only through `process_util::no_window_command` (Windows `CREATE_NO_WINDOW`, Unix own process group, null stdin, scrubbed provider keys; raw `Command::new` is banned by `just guard` and `clippy.toml` `disallowed-methods`). The Windows shell prefers `pwsh -NoLogo -NoProfile -NonInteractive -OutputFormat Text` (fallback `cmd /C`) with `#< CLIXML` stderr decoded to plain text and `PYTHONUNBUFFERED=1`; a timeout kills the whole tree (`taskkill /T /F` or a process-group `SIGKILL`). Lifetime containment (`ADR-0010`): Windows children each join their own kill-on-close Job Object through `process_util::spawn_contained`, and Linux/Android children get `PR_SET_PDEATHSIG(SIGKILL)` (audited shim in `bistre_crypto::containment`), so a crashed Bistre never leaves tool, hook, or git-worktree children running. On timeout `run_bounded` walks the live tree before terminating the job and reaping the root; captured stdout/stderr are capped at 32 MiB each. Git worktree calls go through `run_bounded` with a 120 s bound. The app itself starts no processes (`just guard` rejects `Process.run`/`start` in `apps/bistre_app/lib`): the Linux folder picker (`zenity`, then `kdialog`, 600 s), notifications (`notify-send`, with `--` before the text so a title like `--help` stays text), and opening a folder (`xdg-open`, existing absolute directories only, 15 s) go through core's `desktop_helpers` and `run_bounded` (tests: `desktop_helpers::tests`; a live Linux run is `[UNVERIFIED]`).

## 2. Isolated Worktree Sub-Agents, Skills, Hooks & Scheduled Cron Automations
- Sub-agents isolate mutations via guarded `git worktree add --detach` (`crates/bistre-core/src/subagents.rs`), falling back cleanly to a copy-sandbox (skipping `.env` and secret files) when `git` CLI is absent or on Android, returning a summary capped at `MAX_SUBAGENT_SUMMARY_BYTES`.
- Progressive `SKILL.md` Discovery, Workspace Instructions & Memory (`crates/bistre-core/src/skills.rs`, `crates/bistre-core/src/agent_context.rs`): Indexes YAML frontmatter (`name`, `description`) across all configured workspace folders (`agent.workspace_folders` / `agent.workspace_root`) and injects workspace `AGENTS.md` and `CLAUDE.md` instructions, the bounded skills index, and saved memory entries (`memory_entries`) into non-Write chats whenever tools are enabled. Exposes `skill_load` (Tier-0 read-only, strictly confined to canonical `SKILL.md` files inside bound workspace roots and Bistre's skills folder) and `agent_memory` (`list` Tier-0, `save`/`delete` Tier-1). Multi-folder file tools (`read`, `edit`, `grep`, `glob`) route `<folder_name>/...` paths into secondary roots through per-root `cap-std` handles. A chat in a project whose folder is set works in that folder alone, for its tools, `AGENTS.md`, skills, and a scheduled run's worktree (`projects::workspace_roots_for`; an unreadable chat or project is an error, so a run never falls back to another folder), and every reply in a project sends the project's instructions under `[Project instructions]` after the mode prompt (`projects::append_project_instructions`). Test: `projects_tests::a_chat_in_a_project_sends_its_instructions_and_uses_its_folder`.
- Web search & MCP permissions: `agent.web_search` (`""` Off, `"duckduckgo"`, or custom HTTP(S) URL template supporting `{query}` or `?q=`/`&q=`) directly controls `web_search` tool exposure and dispatch through `PublicWebTransport`. Tool permissions in `agent.tool_permissions` include `web_search` and global `mcp` fallback (`Off` suppresses all MCP tools), and individual MCP servers toggle cleanly via `enabled` in `agent.mcp_servers`. Tests: `egress_tests::agent_web_search_setting_controls_tool_exposure`, `agent_prompt_injects_claude_md_skills_and_memory_in_chat_mode`, `agent_catalog_exposes_skill_load_and_agent_memory_tools`, `agent_context::tests::build_web_search_url_supports_ddg_and_custom_templates`, `apps/bistre_app/test/agent_settings_wiring_test.dart`.
- Local Workspace Lifecycle Hooks (`crates/bistre-core/src/hooks.rs`): Executes configured `.bistre/hooks.json` hooks (`PreToolUse`, `PostToolUse`, `RunFinished`, `RunFailed`) through `run_bounded` with hard timeouts (1-60 s) and stripped provider API keys. Hooks run only after the user approves them in Settings > Agent: the approval stores the `blake3` digest of the exact file (`agent.hooks_approved:<root hash>`), so any edit needs a new approval, and `approve_workspace_hooks` refuses a digest that no longer matches the file (`hooks_changed`). An unapproved, failing (non-zero exit), or unrunnable pre-tool hook blocks the call with an error tool result and `diag.hooks.approval_required` (unapproved); post-tool hook failures are logged. Hooks race the run's cancel signal. The file is capped at 64 KiB; an unreadable or malformed file is an error. Tests: `hooks::tests`, `approval_flow_tests::pre_tool_hooks_need_approval_and_a_failing_one_blocks_the_call`, `apps/bistre_app/test/workspace_hooks_test.dart`.
- Fail-closed tool policy: an unreadable `agent.tool_permissions` map (storage error or not a JSON object) blocks every tool except Tier-0 reads and hides the write tools (`ActiveToolCatalog.policy_unreadable`). Tool arguments that are not a JSON object are an error tool result with no permit (an empty string means no arguments), never an empty `{}` call. Tests: `approval_flow_tests::an_unreadable_permission_map_blocks_everything_but_reads`, `malformed_tool_arguments_are_an_error_not_an_empty_call`.
- Live shell output (`shell_progress.rs`): a running `shell` call streams its output to the tool row as `ToolExecutionUpdated { status: "running" }`, at most one event per 250 ms carrying the last 16 KiB; a slow reader loses progress copies, never captured output (`process_util::run_bounded_with_progress`). Tests: `output_arrives_while_the_command_still_runs`, `progress_is_coalesced_and_bounded`.
- Bistre's skills (`crates/bistre-core/src/skill_install.rs`): `<data dir>/skills/<name>/SKILL.md`, listed after workspace skills and offered with `skill_load` in every chat with tools on, a workspace or not. A skill installs from a folder holding `SKILL.md`, a `SKILL.md` file, a zip (the folder of its shallowest `SKILL.md`), or a GitHub link (`https://github.com/<owner>/<repo>[/tree|blob/<ref>/<path>]`, downloaded as `archive/<ref>.zip` through `PublicWebTransport`, a repository link as `HEAD`); each holds at most `MAX_SKILL_FILES` (200) files and `MAX_SKILL_BYTES` (8 MiB), zips at most 32 MiB, symlinks, `.git`, and zip entries that climb out of their folder are skipped. The folder is named by the skill's `name` (lowercase letters, digits, hyphens), written beside the old one and swapped in by rename, so a reinstall replaces it and a failed one leaves it. Save as skill turns a reply into a new skill named by its chat (a numbered name when taken, never a replacement). Tests: `skill_install::tests`.
- Read-only Plan mode: Plan mode hides write tools and is also enforced where tools run: every call that is not a Tier-0 read (edit, shell, MCP, or a tool the model calls anyway) gets an error result "Refused: this chat is in read-only Plan mode" without asking or running (`ActiveToolCatalog::read_only`). Test: `approval_flow_tests::plan_mode_refuses_every_write_even_when_the_model_calls_one`.
- Step limit: a run that reaches `MAX_RUN_STEPS` (24) while the model still wants to go on (tool calls pending, tools just ran, or a paused turn) ends as failed with `diag.run.step_limit_reached`, never as a silent "complete". Test: `egress_tests::a_run_stopped_by_the_step_limit_says_so`.
- Recalling condensed messages (`history_search`, `history_open`, Tier-0, replay-safe; `crates/bistre-core/src/history_recall.rs`): offered only while a compaction summary leads the history being sent and tools are on (each can be set to Off). `history_search` searches the messages the latest summary condensed, after the context-start pin: every query word (up to 200 characters) must appear, any case; up to 20 matches with id, role, and a 240-character excerpt, plus `more`. `history_open` returns one saved message of the active branch (after the pin) in parts of 8,000 characters with an `offset` to read on. The step label is the query or the message's first line. Tests: `history_recall::tests`, `egress_tests::compaction_follows_the_users_words_and_the_edited_summary_is_sent`.
- Chat goal (`/goal`, `crates/bistre-core/src/goal.rs`, `kv_meta` `thread_goal:<chat id>`, at most `MAX_GOAL_CHARS` (2,000) characters, control characters dropped): an open goal is added to the system prompt outside Write mode, and while tools are on the model gets `goal_complete` (Tier-0, `summary` and `verification` both required), which closes the goal. When a run would end with the goal open and nothing queued, Bistre sends a goal-check message (`goal_check: true`, shown as a quiet note) asking the model to check its work against the goal, at most `MAX_GOAL_CHECKS` (3) times after each message you write; each is a paid request reserved like any other. Tests: `goal::tests`, `tests::an_open_goal_sends_bounded_work_checks`.
- Asking the user (`ask_user`, Tier-0): the model asks one question (up to 2,000 characters) with up to 4 short answer options. The run ends after that tool batch (other calls in it get "Not run: the run stopped to wait for the user's answer."), the feed shows the question with one button per option, and the user's next message, sent under the question, is the answer. Tests: `approval_flow_tests::asking_the_user_ends_the_run_and_the_next_message_answers`, `apps/bistre_app/test/committed_tool_steps_test.dart`.
- Helpers (`agent_delegate`, `crates/bistre-core/src/delegate.rs`, off by default): up to 3 read-only helpers run in parallel on the run's provider and model, each a short in-memory conversation of at most 8 requests that may use only the read tools the run may use (`read`, `grep`, `glob`, `fs_list`). Helpers never write, ask for approval, or start helpers; each request is reserved and settled in the Wallet Shield like the run's own, and Stop ends every helper. Their capped summaries return as one tool result. Test: `approval_flow_tests::a_helper_reads_with_read_tools_only_and_reports_back`.
- Scheduled Cron & Interval Automations (`crates/bistre-core/src/cron.rs`): interval (`every 30s/15m/2h/1d`) and full 5-field UTC cron (`*`, `*/N`, values, ranges, stepped ranges and lists in every field; day of month and day of week combine with OR as in standard cron; searched up to four years ahead so Feb 29 is found). A bad schedule turns its job off with `last_status = invalid_schedule` and never fires (it became "every hour"). A due job starts its real run (`InProcessEngine::start_scheduled_run`: a new chat named after the job, in the job's project when it has one, with its assistant and mode, sent its prompt; `last_run_id` records it). The run record holds the job's unattended policy and worktree (`agent::RunApprovalPolicy`, read once per run; an interactive run records `PauseAndNotify`). A call that needs approval then waits in the chat (`PauseAndNotify`), is refused with a tool result while the run goes on (`DenyTier2AndContinue`, Skip & continue), or runs without asking when the run has its own worktree and the tool works in the workspace (`SandboxWorktreeAuto`, Sandbox auto: file tools and the shell; MCP, web, paid tools, and computer use still wait; no worktree means every such call waits). A Sandbox auto job gets `use_worktree`: its run works in a new `git worktree add --detach` (or filtered copy) of the first workspace folder under `<data dir>/scheduled_worktrees`, kept for review, at most `MAX_SCHEDULED_WORKTREES` (8), the oldest removed first. The daemon's housekeeping sleeps 1 s to 5 min until the next deadline and wakes only on run start, end and state changes, never on streaming deltas. Tests: `cron::tests::all_five_cron_fields_are_honoured`, `a_bad_schedule_turns_its_job_off`, `old_scheduled_worktrees_are_removed_beyond_the_cap`, `egress_tests::a_due_scheduled_job_starts_a_run_with_its_prompt`, `approval_flow_tests::a_scheduled_run_under_skip_refuses_approvals_and_goes_on`, `a_scheduled_sandbox_run_edits_its_worktree_without_asking`, `sandbox_auto_without_a_worktree_waits_for_the_user`, daemon `housekeeping_tests`.
- Sleep-Immune Durable Runs & Mid-Stream Steering (`ADR-0013`): Every agent run and step journals to SQLite WAL (`agent_runs`, `run_steps`, `steering_queue`) behind OS sleep leases (`PowerCoordinator` / Win32 `PowerCreateRequest` / Linux `systemd-inhibit` / Android `BistreAgentService` `specialUse` FGS + optional `TermuxBridge`). Mid-stream user steering messages inject cleanly at step boundaries without cancelling active generations.

## 3. MCP Client (Streamable HTTP, Spec `2026-07-28` + Legacy Fallback)
- Bistre's own client (no SDK, `ADR-0018`) speaks `2026-07-28` first and `2025-11-25` as the legacy fallback (`crates/bistre-core/src/mcp_era.rs`, checked against the `2026-07-28` changelog, versioning, stdio, `server/discover`, and cancellation pages). A `server/discover` probe settles the era once per stdio process or HTTP server:
  - A result naming `2026-07-28` in `supportedVersions` is modern: no `initialize`, and every request carries `_meta` (`io.modelcontextprotocol/protocolVersion`, `clientInfo`, `clientCapabilities`).
  - An MCP-reserved error code (-32020 to -32099, such as `UnsupportedProtocolVersion` in an HTTP 400 body) or a result without our version is surfaced, never answered with `initialize`.
  - Any other JSON-RPC error, an HTTP 4xx, or a stdio probe silent for `MCP_DISCOVER_PROBE_TIMEOUT` (10 s) is legacy and gets `initialize`; a legacy reply without `protocolVersion` fails. A crash, a 5xx, or a blocked host is the error it is.
  - `server/discover` lists no tools, so discovery always sends `tools/list`, following `nextCursor` page by page (HTTP and stdio, `mcp_era::take_tools_page`) for at most `MAX_TOOL_LIST_PAGES` (20) pages; a repeated or empty cursor ends the walk, and a server still paging after the limit keeps its later tools unlisted (logged). Tests: `mcp::tests::http_discovery_follows_next_cursor_and_stops_on_a_repeat`, `mcp_stdio_tests::discovery_reads_every_tools_page`.
  - Only a complete result is used: no `resultType` (earlier revisions) is complete, and `input_required` (multi round-trip) fails closed with `mcp_input_required`, since Bistre answers no server requests.
  - Tasks extension (`crates/bistre-core/src/mcp_tasks.rs`, checked against the extension's `2026-07-28` schema): every modern request declares `io.modelcontextprotocol/tasks` in `clientCapabilities.extensions`. A `tools/call` answered with a task handle (`resultType: "task"`, flat `taskId`) is polled with `tasks/get` at the server's `pollIntervalMs`, clamped to 250 ms to 10 s, for at most `MAX_TASK_WAIT` (30 minutes), and the finished task's `result` is the tool's answer. A failed task is its JSON-RPC error; a task that needs input (`input_required`, since Bistre answers no server requests) or outlives the limit is cancelled with `tasks/cancel` and fails; a stopped run stops polling and the server's task expires by its own TTL. Tests: `mcp_tasks::tests`, `mcp_stdio_tests::a_task_handle_is_polled_until_the_tool_finishes`.
  - Older servers: a legacy server's `initialize` answer sets the session's version, so a `2025-03-26` server is used at its own version. Test: `mcp_stdio_tests::a_2025_03_26_server_is_used_at_its_own_version`.
  - Not used: the `resourceSubscriptions`, `resourcesListChanged`, and `promptsListChanged` listen filters, since Bistre reads no resources or prompts.
  - List freshness (`crates/bistre-core/src/mcp_refresh.rs`): `ttlMs` and `cacheScope` are read from each `tools/list` result page (the shortest `ttlMs`; private when any page says `private`). Discovery stores the list with the time it was fetched (`kv_meta` `mcp.tools_fetched_ms:<server id>`) and the token it was fetched with (`mcp.tools_auth:<server id>`, a keyed BLAKE3 of the token, never the token). When a message is sent, each enabled server whose list is past its `ttlMs` or reported a change is listed again in the background (one refresh per server at a time), and the send never waits; a private list fetched with another token is emptied before the run, so a run never sees it. A list without `ttlMs` and no change is kept until the user discovers again. Tests: `mcp_refresh::tests`, `mcp::tests::the_list_cache_fields_come_from_every_page`.
  - Server token: Settings > Agent gives each HTTP server a token field (`set_mcp_token`); the token goes to the vault (`mcp_bearer:<server id>`, at most 8 KiB), is sent as `Authorization: Bearer` only over HTTPS or to a loopback host, is never shown again, and is removed with its server. Test: `library_actions_test.dart`.
  - Change notices (`subscriptions/listen`, `crates/bistre-core/src/mcp_listen.rs`): each enabled HTTP server last reached as `2026-07-28` gets one listen stream asking only for `toolsListChanged`, opened with the first message sent and kept until the app closes or the server list changes. A stream stays open at most `LISTEN_STREAM_MAX` (1 hour) and 4 MiB, then opens again after 5 s, doubling to 10 minutes and starting over after a stream that stayed open 10 minutes; a server that leaves `toolsListChanged` out of its acknowledgement, answers with an error or a `4xx`, or fails 8 opens in a row is not asked again until its address or token changes. A `notifications/tools/list_changed` relists the server at once. A modern stdio session sends the same request after `server/discover` without waiting, and a change notice read among later answers marks the list for the next send. Tests: `mcp_listen::tests`, `mcp_stdio_tests::a_modern_session_listens_for_tool_list_changes`.
  - Tests: `mcp_era::tests`, `mcp_stdio_tests::{a_modern_server_gets_meta_on_every_request_and_no_handshake, a_legacy_server_falls_back_to_initialize, an_input_required_result_fails_closed}`, `mcp::tests::{a_modern_http_server_is_discovered_without_initialize, a_modern_protocol_error_never_falls_back_to_initialize, an_http_input_required_result_fails_closed}`.
- Explicitly omits deprecated MCP features (Roots, Sampling, Logging, HTTP+SSE, OAuth DCR).
- MCP over stdio (`crates/bistre-core/src/mcp_stdio.rs`): ONE long-lived session (process) per server, reused by every call (2026-07-28 stdio: clients "should not use an individual task, thread, or conversation as the lifetime boundary"), so ordinary use never spends the `3 starts / 10 min` restart budget. The child is held for the session's life (the command sets `kill_on_drop`; the old code dropped it at spawn, killing every server at once). A broken session (crash, timeout, endless line) is dropped, killing its tree at once, and the next call starts a new one; a crashed call is never resent. A call whose caller stops waiting (a stopped run drops it) sends `notifications/cancelled` with its request id, so the server stops work nobody will read. A command/args change starts a new session after closing the old one; saving the server list closes every session (and resets the restart budgets), and so does engine shutdown. Closing is graceful: stdin closes, the server gets `STDIO_SHUTDOWN_GRACE` (5 s) to exit, then the tree is killed (child pipe reads run on the blocking pool, so an open session would also block runtime shutdown). Stdout lines are read bounded at `MAX_STDIO_LINE_BYTES` (1 MiB). A message with a `method` is the server's request or notification, never our response even when it reuses our id: `ping` gets `{}`, anything not negotiated (e.g. `roots/list`) gets `-32601`. JSON-RPC errors on stdio and HTTP alike become errors carrying the code and the server's message (`mcp::json_rpc_result`). Tests: `mcp_stdio_tests.rs` (the test binary re-runs itself as a mock server: `calls_share_one_session_per_server`, `server_requests_are_answered_not_taken_as_responses`, `a_broken_session_is_killed_and_replaced`, `a_crashed_server_is_restarted_for_the_next_call`, `a_dropped_call_sends_cancelled_to_the_server`, `closing_a_session_lets_the_server_exit_on_its_own`), `mcp::tests::an_http_json_rpc_error_is_an_error_not_a_result`.
- MCP Registry search (`crates/bistre-core/src/mcp_registry.rs`): `GET https://registry.modelcontextprotocol.io/v0.1/servers?limit=20&version=latest[&search=][&cursor=]` through `PublicWebTransport` (2 MiB cap; response shape `servers[].server{name, title?, description, version, remotes[], packages[]}` + `metadata.nextCursor`, checked against the live registry). Each result becomes a turned-off `McpServerConfig`: the first `streamable-http` HTTPS remote with no URL template and no required header or variable, else an `npm` (`npx -y id@version`) or `pypi` (`uvx id==version`) stdio package with no required environment variable or argument whose name and version are plain tokens (letters, digits, `@ / . _ - +`, never starting with `-`). Anything else is left out, and a body that is not the registry's shape is an error. Tests: `mcp_registry::tests`.
- Noisy Server Resilience (the stdio transport keeps the 64 KiB `stderr` ring and non-JSON `stdout` quarantine): caps per-tool result payloads at 256 KiB (spilling overflow to local artifacts) and sorts exposed tool schemas deterministically for LLM prompt-cache stability.

## 4. Harness Precision & Web Safety
- Stale-read guard (`tools::ReadLedger`): every `read` records the file digest per scope (thread); an `edit` after the file changed on disk fails with `DiagnosticKey::ToolStaleRead`. Failed edits return a near-miss hint (`target_not_found;near_line=N`); CRLF files keep CRLF when the model sends LF text; partial reads end with a footer telling the model never to rewrite a whole file from a truncated view.
- One dispatch gate (`crates/bistre-core/src/approval.rs`): each approved call becomes a one-use, non-`Clone`, non-serializable `ToolExecutionPermit` bound to `(thread, tool, arguments digest, policy revision)` and claimed with an atomic compare-exchange; `save_settings` calls `invalidate()` synchronously. Approval is a separate step: `approve_tool_call(thread, tool, arguments)` (called when the user approves) stores the permit for 60 s (at most 64 outstanding) and returns its id; `execute_workspace_tool(..., permit_id)` removes it and claims it against the exact arguments. Only Tier-0 read-only calls are auto-issued, by core policy, never by the caller. Tier-3 calls fail with `diag.tool.tier_blocked`. Tests: `approval.rs` and `non_read_only_tools_require_an_exact_user_approval` in `crates/bistre-core/src/tests.rs`. `RunActivity` times steps on a monotonic clock that ignores gaps > 5 s (sleep).
- Live approvals in a run (`crates/bistre-core/src/agent_tools.rs`): a paused call emits `ToolApprovalRequested { thread_id, run_id, call_id, .. }` and waits in `PendingApprovalMap` under `ApprovalKey { thread_id, run_id, call_id }`; `respond_tool_approval(thread_id, run_id, call_id, decision)` releases exactly that waiter, so two chats paused on the same provider id (an empty id becomes `call_0`) never release each other. Decisions: `approve_once`, `approve_for_thread` (an `ApprovalMemory` chat grant for the exact tool + canonical-argument digest; any arguments only for Tier-0 reads), `deny` (the identical call is refused for the rest of the run without asking: "already denied"), and `stop` (refuse and cancel the run). Memory is bounded at 1,024 entries, run denials are forgotten when the run ends, chat grants when the chat is deleted. The wait has no time limit and does not poll: only the decision, the run's cancel signal (via its `wake` `Notify`), or a dropped responder (deny) ends it, and `PowerCoordinator::pause_for_user` gives back the keep-awake lease while waiting. Tests: `agent_tools::approval_flow_tests`, `apps/bistre_app/test/approval_flow_test.dart`.
- Provider tools: Gemini and Anthropic can also read links and run code on their own servers beside these tools (Spec 02 "Provider tools"); Bistre's `web_fetch` and `web_search` stay the fallback for every provider.
- `PublicWebTransport` (`crates/bistre-core/src/ssrf.rs`): `web_fetch` and the pricing registry use a dedicated client with public-IP pinning at connect time (custom DNS resolver), `.no_proxy()`, `Policy::none()` plus ≤ 6 manually re-validated redirects, full IANA IPv4/IPv6 special-purpose exclusions (CGNAT, ULA, documentation, 6to4/Teredo, NAT64 and IPv4-mapped unwrapping), `*.localhost` / scoped `%zone` / embedded-credential rejection, a 2 MiB streamed body cap, and fail-closed construction.
- MCP over HTTP (`mcp::McpHttpTransport`): loopback servers use a dedicated no-proxy, no-redirect client; every other host goes through `PublicWebTransport` (private LAN hosts are refused). The era (and a `2025-11-25` server's `Mcp-Session-Id`) is remembered per server id and URL (at most 64 servers; saving the server list forgets the removed and edited servers and closes their legacy sessions with `DELETE` in the background, and a list that does not parse forgets and closes all; test `mcp_tests::a_dropped_servers_legacy_session_is_closed_with_delete`), so a stateful legacy server keeps its state across the tool calls of a run; an HTTP 404 on an existing session renews it exactly once. The era is settled before `tools/call`, so the call is sent exactly once: any other failure, a 400 included, is an error and is never resent (it may already have run). A failed request (not a JSON-RPC error answer) forgets the era and closes a legacy session with `DELETE`, so the next call probes again. Tests: `mcp::tests::{a_legacy_session_is_reused_across_calls, a_failed_tool_call_is_never_resent_and_the_session_is_closed}`. Per-call timeout 60 s, responses capped at 1 MiB before the 256 KiB render cap. Also: `3 starts / 10 min` stdio restart budget that never resends the call that discovered the crash, stable `mcp__<server>__<tool>` names (≤ 64 chars), bearer tokens only over HTTPS or loopback, and a deferred `mcp_schema` tool once more than 6 MCP tools are exposed to a model.
- Skills: discovery indexes at most 64 `SKILL.md` files and skips files above 512 KiB without reading them; skill and `AGENTS.md` bodies are read raw (never through the line-numbered `read` tool).
- Computer use (desktop) & Phone use (Android) (`crates/bistre-core/src/computer_use.rs`, `apps/bistre_app/windows/runner/flutter_window.cpp`, `apps/bistre_app/android/app/src/main/kotlin/dev/bistre/bistre_app/BistrePhoneUseService.kt`): one `computer_use` tool (`screenshot`, `click`, `double_click`, `right_click`, `move`, `type`, `key`, `scroll`) with strict boundary validation (`text <= 4,000` chars, `key <= 64` chars, coords `0..=16,384`, scroll `-10,000..=10,000`). Off by default (`settings.ui_prefs.computerUseEnabled`), never exposed in Plan/Write mode or to sub-agents, and every call requires fresh per-call approval (never auto-approved by preset, tool-allow policy, or `ApproveForThread`). Rust emits `EngineEvent::HostActionRequested` and waits via `HostActionBroker` (racing cancel + 60 s timeout); Dart invokes the native platform bridge (`bistre/desktop_host` `computerUse` on Windows via Win32 `SendInput` + GDI/WIC PNG ≤ 1280 px, or `bistre/phone_use` `phoneUse` on Android via `BistrePhoneUseService` AccessibilityService) and returns the result via `respond_host_action`. Screenshots remain transient in memory for the immediate next turn and are never stored to SQLite or disk. Android labels the feature Phone use in all locales; Linux Wayland hides the setting until RemoteDesktop portal support is verified. ## Context accounting
- Tool schemas count schema by schema (`ActiveToolCatalog::schema_tokens`); the breakdown's Built-in and MCP rows add up to exactly what a run counts (`context_breakdown::tests::tool_rows_sum_to_the_tokens_a_run_sends`). Deferred MCP schemas (behind `mcp_schema` past 6 tools) are listed as not sent and never added to the total.
- The history estimate includes what replay sends besides text: tool calls (name and arguments) and reasoning blocks (`compaction::tests::tool_arguments_and_reasoning_are_counted`); the proactive shorten before a request adds the tool schemas and runs once the window is `AppSettings.auto_compact_at_percent` full (default 85 %, set in Settings > Default models with a slider or a typed number; core clamps it to 50-95 %, `compaction::auto_compact_reserve_percent`). The context gauge's reserve uses the same point.
