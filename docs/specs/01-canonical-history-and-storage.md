# Spec 01: Canonical Local History & SQLite WAL Storage

## 1. Canonical Local-First Sovereignty & Dev/Prod Isolation
Bistre owns the master conversation graph locally in `<data_dir>/bistre.sqlite`. Provider-side state IDs (`previous_response_id`, `previous_interaction_id`) are strictly optional disposable cache pointers stored in `provider_meta_json` and never required to read, branch, export, or replay history (`ADR-0004`, `ADR-0005`).
- Dev vs Production Data Directory Separation: Production builds store SQLite and OS-encrypted `SecretVault` data under `%LOCALAPPDATA%\Bistre` (Windows) / `$XDG_DATA_HOME/bistre` (Linux) / app private data dir (Android). Debug builds (`kDebugMode`) automatically isolate both SQLite and `SecretVault` inside `<repo>/.bistre-dev/` (gitignored) so local development never collides with real user data; `BISTRE_DATA_DIR` overrides either mode explicitly.
- WAL-Safe Backups & Conversation Export: `backup_database(dest_path)` performs an atomic `VACUUM INTO` hot snapshot without stalling readers, and `export_thread(thread_id, format)` renders full conversation history to Markdown or JSON.

## 2. Concurrency & WAL Configuration
- Single-Writer Actor: Exactly one dedicated thread (`bistre-sqlite-writer`) holds the `READ_WRITE` SQLite connection behind a bounded `SyncSender` (`cap=256`). Write transactions are strictly short and never span `.await` or network I/O, eliminating write-write `SQLITE_BUSY`.
- Short-Lived Readers: Read queries open read-only connections and immediately drop statements after mapping rows so long-lived snapshots never starve WAL checkpoints.
- Required PRAGMAs:
  - `PRAGMA journal_mode = WAL;` (writer)
  - `PRAGMA synchronous = NORMAL;` (writer)
  - `PRAGMA busy_timeout = 5000;`
  - `PRAGMA foreign_keys = ON;`
  - `PRAGMA journal_size_limit = 8388608;` (8 MiB cap, Spec 11 §3)
  - `PRAGMA wal_autocheckpoint = 1000;` (writer)
  - `PRAGMA temp_store = MEMORY;`
- Checkpointing & Reclaim: Clean shutdown runs `reclaim_storage()` = `PRAGMA wal_checkpoint(TRUNCATE)` + `PRAGMA optimize` and logs `(busy, log_frames, checkpointed_frames)`.

## 3. Schema v8 DDL (`PRAGMA user_version = 8`, Additive Expand over v5 → v6 → v7 → v8)
- `workspaces(id TEXT PRIMARY KEY, name TEXT NOT NULL, root_path TEXT, created_at_ms INTEGER NOT NULL)`; v12 adds `instructions TEXT NOT NULL DEFAULT ''` (section 7, Projects)
- `assistants(id TEXT PRIMARY KEY, name TEXT NOT NULL, role_subtitle TEXT NOT NULL, system_prompt TEXT NOT NULL, default_mode TEXT NOT NULL, badge_code TEXT NOT NULL, icon_slug TEXT NOT NULL DEFAULT '', default_provider_id TEXT NOT NULL DEFAULT '', default_model_id TEXT NOT NULL DEFAULT '', temperature_milli INTEGER, max_output_tokens INTEGER, top_p_milli INTEGER, is_builtin INTEGER NOT NULL DEFAULT 0, created_at_ms INTEGER NOT NULL)`: zero hardcoded preset personas or forced mode pills; fresh installations seed strictly a single neutral `Default` assistant (`default_assistant`) only when the `assistants` table is empty, with full user CRUD (`create_assistant`, `update_assistant`, `delete_assistant` keeping at least one assistant).
- `providers(id TEXT PRIMARY KEY, name TEXT NOT NULL, dialect TEXT NOT NULL, base_url TEXT NOT NULL, default_model TEXT NOT NULL DEFAULT '', key_hint TEXT NOT NULL DEFAULT '', icon_slug TEXT NOT NULL DEFAULT '', custom_icon_path TEXT NOT NULL DEFAULT '', is_enabled INTEGER NOT NULL DEFAULT 1, is_builtin INTEGER NOT NULL DEFAULT 0, use_server_state_cache INTEGER NOT NULL DEFAULT 0, created_at_ms INTEGER NOT NULL, updated_at_ms INTEGER NOT NULL)`: seeded with the Big 3 starters (`openai`, `google_gemini`, `anthropic`, once per database: `kv_meta['providers_seeded_v1']`) and the `openrouter` starter (once per database, existing ones included: `kv_meta['providers_seeded_openrouter']`). Every provider (including starters) is freely editable and deletable (`delete_provider` removes the row + clears its vault key; deleted starters are never silently resurrected on relaunch). API keys are never stored in SQLite; only an optional masked `key_hint` lives in `providers` while secrets stay inside the node-local OS `SecretVault` (`bistre-crypto`).
- `threads(id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE, title TEXT NOT NULL, mode TEXT NOT NULL, topic TEXT NOT NULL DEFAULT 'general', assistant_id TEXT NOT NULL DEFAULT 'default_assistant', is_pinned INTEGER NOT NULL DEFAULT 0, active_head_node_id TEXT, provider_id_override TEXT, model_id_override TEXT, system_prompt_override TEXT, temperature_milli INTEGER, max_output_tokens INTEGER, top_p_milli INTEGER, created_at_ms INTEGER NOT NULL, updated_at_ms INTEGER NOT NULL)`: indexed by `idx_threads_pinned_updated(is_pinned DESC, updated_at_ms DESC)`.
- `nodes(rowid INTEGER PRIMARY KEY, id TEXT UNIQUE NOT NULL, thread_id TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE, parent_id TEXT REFERENCES nodes(id), role TEXT NOT NULL, content TEXT NOT NULL, provider_meta_json TEXT, created_at_ms INTEGER NOT NULL)`: supports single-node deletion (`delete_node`, reparenting children cleanly), deleting a message with everything after it (`delete_from_node`: one transaction over the subtree and its attachment rows; the head moves to the parent when it was inside), clearing a chat's messages while keeping the chat (`clear_thread_messages`), copying a branch into a new chat (`fork_thread`: new ids, references to the old ids in metadata rewritten, attachment rows copied with the stored files shared; test `thread_tests::a_branch_copies_into_a_new_chat_and_a_turn_deletes_with_what_follows`), reversible `compaction_summary` nodes, and user prompt edit-and-branch (`edit_user_node_and_stream`).
- One graph per thread: `append_node` refuses a `parent_id` that is missing or belongs to another thread (`diag.storage.parent_thread_mismatch`), in the same writer transaction as the insert. The app commits a chat switch only after the new chat's messages and draft have loaded, blocks sending meanwhile, and writes the result of any in-flight send, mode change, or reload only into the chat that is still open. Tests: `bistre-storage` `a_parent_from_another_thread_is_refused`, `apps/bistre_app/test/thread_switch_test.dart`.
- `drafts(thread_id TEXT PRIMARY KEY REFERENCES threads(id) ON DELETE CASCADE, text TEXT NOT NULL, updated_at_ms INTEGER NOT NULL)`
- `wallet_ledger(id TEXT PRIMARY KEY, thread_id TEXT, job_id TEXT, provider_id TEXT NOT NULL, model_id TEXT NOT NULL, cost_micros INTEGER NOT NULL, input_tokens INTEGER NOT NULL DEFAULT 0, output_tokens INTEGER NOT NULL DEFAULT 0, status TEXT NOT NULL, created_at_ms INTEGER NOT NULL, purpose TEXT NOT NULL DEFAULT 'chat')` (`purpose` is what the request was for, see Spec 06)
- `ota_state(slot TEXT PRIMARY KEY, active_version TEXT NOT NULL, last_healthy_version TEXT, boot_attempts INTEGER NOT NULL DEFAULT 0, updated_at_ms INTEGER NOT NULL)`
- `kv_meta(key TEXT PRIMARY KEY, value TEXT NOT NULL)`: stores persisted `AppSettings` JSON (`app.settings.v1`, including typography, local font paths, accent hex, nullable Unlimited budget ceiling, OTA feed/channel, sleep-guard/battery/daemon/Termux preferences, window bounds, and custom shortcuts), `providers_seeded_v1` and `providers_seeded_openrouter` (each starter group seeded once), `thread_context_start:<id>`, and provider custom header/body overrides.
- `nodes_fts`: `VIRTUAL TABLE nodes_fts USING fts5(content, content='nodes', content_rowid='rowid', tokenize='unicode61')` maintained atomically via `AFTER INSERT`, `AFTER UPDATE OF content`, and `AFTER DELETE` triggers. Since v11 a second index, `nodes_fts_tri` (`tokenize='trigram'`), is kept by its own three triggers (section 8).
- Storage cleanup keeps staged updates: "Clean unused files" removes unfinished downloads (`.partial`, `.tmp`) and update slots for versions no longer newer than the running one; a staged, newer update (`ota_staging/<version>/payload.bin`) is kept for install. Test: `storage_files::tests::cleaning_keeps_a_staged_update`.
- Schema v6 Durable Harness Tables (`ADR-0013`): `agent_runs`, `run_steps` (with `idempotency_key` & `risk_tier`), `steering_queue`, `workspace_checkpoints` (blake3 pre/post hashes + pre-image content for 1-click Rewind), `attachments`, `memory_entries` (cross-chat pinned/global/workspace memory), `cron_jobs` (scheduled interval & 5-field UTC automations), and `engine_events_log` (monotonic cursor replay log for daemon reconnects).
- Schema v7 Writing & Roleplay Studio Tables (`ADR-0015`): `character_cards` (CCv3/V2 cards + alt-greetings), `user_personas`, `story_books`, `story_entries` (unified Codex + Lorebook V3 keys/secondary keys/decorators/sticky/cooldown/delay), `story_progressions` (chronological chapter-gated updates), `story_chapters` (with Continuity Librarian `era_summary`), `story_scenes` (`beats_text` + `prose_text` + word count), `story_thread_state` (active cast, Author's Note `@D`, Story Memory, creative samplers, dialogue styling), `regex_rules` (scoped linear-time rules), and `story_snapshots` (automatic Time Machine revision history).

## 4. Expand-Contract Migrations & Disk-Full Resilience
- Every schema change runs inside `BEGIN IMMEDIATE ... PRAGMA user_version = N; COMMIT;` followed by `PRAGMA foreign_key_check;` and `PRAGMA quick_check;`.
- All migrations must be additive-only for ≥1 full release cycle (Expand phase) so an `N-1` binary reinstalled after an OTA update can open and read an `N` database cleanly. Pre-migration backups write `<db>.pre-vN.bak` (verified for `v1 -> v2`, `v2 -> v3`, `v3 -> v4`, `v4 -> v5`, `v5 -> v6`, and `v6 -> v7`).
- `SQLITE_FULL` maps to `DiagnosticKey::StorageDiskFull` (never panics), pausing cache/compaction writes while retaining in-memory unsent drafts.

## 5. Schema v8 Expand (`harness::SCHEMA_V8_EXPAND_SQL`)
- `idx_threads_pinned_recent ON threads (updated_at_ms DESC) WHERE is_pinned = 1`: partial index so pinned lists never scan unpinned chats.
- `run_steps.result_overflow BLOB`: step output above 64 KiB is spilled here; `output_json` keeps a `{ "overflow": true, "bytes", "preview" }` stub (first 4 KiB) so run lists never load large tool results; `load_run_step_output(step_id)` hydrates lazily.
- Pre-migration backup `<db>.pre-v8.bak`; `N-1` (v7) binaries ignore the new column and index.
- Spend accounting is fork-safe by construction: each streamed reply writes exactly one `wallet_ledger` row, so branching never re-sums earlier usage; unpriced replies record `cost_known: false` in `provider_meta_json` (a conservative lower bound for the spending limit, never a guess).
- Context usage, compaction thresholds, story prompt budgets, and Wallet Shield pre-request estimates count tokens offline via `crates/bistre-core/src/tokenizer.rs` (`tiktoken 5.1.1`, universal `o200k_base` with zero hardcoded model/vendor families, zero runtime network, and zero background threads).

## 6. Schema v9 Performance Indexes (`SCHEMA_V9_PERF_INDEXES_SQL`)
- `idx_nodes_thread_rowid ON nodes (thread_id, id)`: covering thread/id lookup.
- `idx_threads_ws_pinned_updated ON threads (workspace_id, is_pinned DESC, updated_at_ms DESC)`: eliminates `USE TEMP B-TREE FOR ORDER BY` on `list_threads`.
- `idx_wallet_ledger_job ON wallet_ledger (job_id)` and partial `idx_wallet_ledger_reserved ON wallet_ledger (status, created_at_ms) WHERE status = 'reserved'`: eliminates full table scans during request-ID dedupe and active-reservation recovery.
- Read-only connections set `PRAGMA query_only = ON; PRAGMA cache_size = -2000;` so short-lived readers never allocate unbounded page caches. Pre-migration backup `<db>.pre-v9.bak`; `N-1` (v8) binaries read v9 cleanly.

## 7. Schema v10: Privacy Cleanup and Parent Index (`SCHEMA_V10_PRIVACY_AND_PARENT_SQL`)
- A summary is the one rewritable message: `rewrite_compaction_summary` replaces a `compaction_summary` row's text in place (same id, parent, and kept-message link; the search index follows through its update trigger) and refuses every other role with `not_a_compaction_node`. Original messages are never rewritten. Test: `only_a_compaction_summary_can_be_rewritten`.
- What a request sends of the history (`turn_context::project_turn_history`): the active branch after the context-start pin, minus the messages left out of the context, then cut to the history limit. Left out (`crates/bistre-core/src/context_exclusion.rs`, `kv_meta` `thread_excluded:<chat id>`, at most `MAX_EXCLUDED_MESSAGES` (512) ids): only a user or assistant message of the chat can be left out, a left-out reply takes the tool results right after it along, and an unreadable list fails the request instead of sending everything. The history limit (`history_limit.rs`, `kv_meta` `settings.history_message_limit`, 0 or absent for every message) keeps a leading summary, cuts before a message you wrote, and always keeps your latest message. Tests: `context_exclusion::tests`, `history_limit::tests`.
- Branch into a new chat copies the chat's left-out list and goal with the ids rewritten (`fork_thread(.., carried_kv)`); other per-chat values stay with the source. Summarize into a new chat (`resume_from_summary`) copies the chat's settings (assistant, mode, provider and model, prompt) into a new chat whose one message, and head, is a `compaction_summary` root holding the summary; an open goal goes along. Tests: `thread_tests::{a_branch_copies_into_a_new_chat_and_a_turn_deletes_with_what_follows, a_summary_opens_a_new_chat_with_the_source_settings}`.
- Edit reply (`edit_reply`) first stops the chat's running reply, then saves the edited text as a new sibling assistant message on the same parent, keeping the reply's model and usage fields and recording `edited_from`; the original stays as the earlier version. Test: `utility_chat::tests`.
- A chat's files (`chat_files::list`, `StorageHandle::list_nodes_with_files`): the newest 500 messages whose metadata carries `attachments`, read without their text, give at most `MAX_CHAT_FILES` (500) files newest first, each blob once, marked sent (a user message) or made (a reply or tool). Test: `chat_files::tests`.
- Chats zip (`chat_extras::{export_chats_zip, import_chats_zip}`): `chats.json` (the format chat import reads) plus every blob the messages carry under `attachments/`, written to a temporary file renamed into place; a blob missing on disk is logged and left out. Import reads at most 4 GiB and 20,000 entries, checks each file's BLAKE3 against its name before storing it, and stops before any chat is added when one differs. Test: `chat_extras::tests::chats_and_their_files_round_trip_through_a_zip`.
- Opening message: a new chat outside Write mode whose assistant has a `kv_meta` `assistant_greeting:<assistant id>` value starts with it as a root assistant message (`greeting: true`, at most 8,000 characters); deleting the assistant deletes the value. Test: `chat_extras::tests::an_opening_message_starts_the_assistants_new_chats`.
- Erase everything (`data_wipe`): the request is an `erase-on-start` marker in the data folder; the next engine start, under the single-writer lock and before the database and vault open, removes the marker first and then every entry of the data folder except `daemon.lock`, logging any it cannot remove, so an erase runs once. The request can be withdrawn until then. Test: `data_wipe::tests::an_erase_runs_once_and_keeps_the_writer_lock`.
- Deleting a chat deletes what was derived from it: `delete_thread` removes the chat's `engine_events_log` rows, `agent_runs`, `run_steps`, and the `kv_meta` values kept for it alone (keys ending in `:<chat id>`: its checklist, reply prefill, and last-viewed mark) with the chat and its nodes in one transaction. The event log never stores content: `EngineEvent::without_content` keeps ids, states, and counts and drops message text, thinking, tool arguments and outputs, run buffers, and audio; a replay re-reads bodies by id. Tests: `deleting_a_chat_removes_its_event_log_and_run_journal`, `deleting_a_chat_deletes_its_own_saved_values`.
- v9 -> v10 clears the v0.1.2 event log once (its rows held message bodies) and the run journals of chats deleted earlier, and adds `idx_nodes_parent ON nodes(parent_id)` (the foreign-key child lookup every node delete runs) and `idx_agent_runs_thread`. Tests: `v10_migration_clears_old_event_bodies_and_indexes_parents`, `deleting_a_25k_message_chat_removes_every_node`.
- Projects (v11 -> v12, `project_repo.rs`): a project is a `workspaces` row other than the default one (`DEFAULT_WORKSPACE_ID`, which holds every chat outside a project); `threads.workspace_id` names a chat's project. v12 adds the project's `instructions` column, applied with `add_column_if_missing` so a rerun finds it already there; an older app ignores it. `root_path` is the project's folder. Deleting a project first moves its chats to the default workspace in the same transaction, so no chat is lost; the default workspace can be neither saved as nor deleted as a project. Core bounds them (`projects.rs`): at most `MAX_PROJECTS` (200), names of 1 to 120 characters, instructions up to 16,000. Tests: `projects_tests::deleting_a_project_keeps_its_chats`, `v10_migration_clears_old_event_bodies_and_indexes_parents` (reruns every migration over current tables).
- One run per chat at a time: a send, edit, or Regenerate first cancels the chat's running reply and waits up to 5 s (`PREVIOUS_RUN_STOP_TIMEOUT`) for it to finish and commit, so a stopped reply can never commit after, or move the head over, the new one. Test: `egress_tests::regenerate_mid_stream_finishes_the_old_run_before_starting_the_new`.
- Deleting a chat in the app: its running reply is cancelled at once; the 8 s Undo window survives focus changes (desktop `inactive`), and pending deletes are committed when the app is closing (`detached`, or `paused` on a phone). Test: `apps/bistre_app/test/thread_delete_test.dart`.

## 8. Search Resilience and CJK (Schema v11, `SCHEMA_V11_TRIGRAM_SQL`)
- A corrupt search index never blocks saving: node writes run through `write_node_change`. When FTS5 reports `SQLITE_CORRUPT_VTAB` (`DiagnosticKey::StorageSearchIndexCorrupt`), all six search triggers are dropped and `kv_meta.search.fts_stale = 1` is set in one transaction, the write is retried once, and the error is logged. While stale, search is a bounded `LIKE` scan (escaped `%`/`_`, newest first, ≤ 200 hits). The index is never rebuilt live: the next `StorageHandle::open` rebuilds both indexes and restores the triggers before any write; a failed rebuild is logged and search stays on the scan. Tests: `a_corrupt_search_index_never_blocks_writes_and_search_falls_back`, `a_stale_search_index_is_rebuilt_at_the_next_open`.
- CJK and substrings: search tries the ranked word index first, then the trigram index (the query as one quoted phrase) for CJK text and mid-word substrings; queries shorter than three characters use the bounded scan. The trigram index makes the database larger (roughly the size of the text again) [UNVERIFIED size]. Test: `search_finds_cjk_and_substrings`.
- Reopen after a disk I/O error: `SQLITE_IOERR` maps to `DiagnosticKey::StorageIoError`; the writer then replaces its connection, so the next write reaches the database (for example after the machine wakes from sleep). The failed write is not retried, because its commit state is unknown. Test: `the_writer_reopens_its_connection_after_an_io_error`.
