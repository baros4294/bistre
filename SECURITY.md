# Security Policy

## Privacy & Telemetry Guarantee
Bistre collects zero telemetry, zero analytics, and zero crash-report uploads. All conversations, drafts, search indexes, and credentials stay local to the user's device or explicitly QR-paired execution node.

## Security Architecture
- Credentials: Stored only on the execution node, never in SQLite, never across Remote Bridge, never in logs, and always encrypted at rest. Windows: DPAPI (`CurrentUser`) entries in `bistre_vault.dpapi.json`. Android: entries sealed with XChaCha20-Poly1305 under a random data key that a non-exportable Android Keystore AES-256-GCM key (StrongBox when available) wraps; only the wrapped key is stored, in `noBackupFilesDir`. Linux: the same sealing, with the data key held by the Secret Service (`oo7`: D-Bus or the Flatpak portal) or derived with Argon2id from `BISTRE_VAULT_PASSPHRASE` on headless hosts. Each sealed entry binds its name as associated data. Without any key source the Linux vault refuses to store new keys (older plaintext entries stay readable until a key source appears, then are encrypted in place). If the key changes, the unreadable vault is set aside (`*.key-mismatch-<ms>`) rather than deleted.
- Transport: Pure Rust TLS (`rustls` + `rustls-platform-verifier`) honoring OS/enterprise CA trust stores; `openssl-sys` is banned via `deny.toml`. Remote Bridge uses TLS 1.3 mTLS with QR-exchanged certificate fingerprint pinning.
- Tools & Filesystem: Workspace edits require `cap-std` capability-scoped handles (`O_NOFOLLOW`) and `blake3` line-range hash anchors. Every child process is created through `process_util::no_window_command` (Windows `CREATE_NO_WINDOW`, Unix process group, scrubbed provider keys) and its whole tree is killed on timeout. Each Windows child joins its own `KILL_ON_JOB_CLOSE` + `DIE_ON_UNHANDLED_EXCEPTION` Job Object (a crashing child dies instead of showing the fault dialog) and Linux/Android children receive `PR_SET_PDEATHSIG(SIGKILL)` (audited shim in `bistre_crypto::containment`, Spec 04 / ADR-0010), so children never outlive a crashed Bistre.
- Provider tools (off by default, per provider): with Gemini's or Anthropic's own tools on, the provider's servers fetch the links the model reads and run its code; Bistre sends nothing extra itself, and the provider sees those links as it sees the chat.
- Network Egress for Model-Directed Traffic: `web_fetch`, remote MCP servers, and pricing-catalog GETs use `PublicWebTransport` (public-IP pinning at connect time, no proxy, re-validated redirects, IANA special-purpose IPv4/IPv6 exclusions, streamed body caps). Loopback MCP servers use a separate no-redirect client; private LAN hosts are refused. An HTTP MCP server's token is kept in the vault, sent only over HTTPS or to a loopback host, and removed with its server. A remote MCP server's `subscriptions/listen` stream uses the same rules on a client without a read timeout (each stream is limited to 1 hour and 4 MiB), and opens only for an enabled server after a message is sent. Pricing-catalog GETs (OpenRouter models, images, and videos lists; LiteLLM) send no identifiers and run only while a non-local provider is streaming. A skill installed from a GitHub link is one `GET` of that repository's archive through the same transport, only when the user presses Install. MCP Registry searches (`registry.modelcontextprotocol.io`) use the same transport, run only when the user opens the registry browser, and send only the typed search text; a server added from the registry is saved turned off, so its command or address is shown before anything starts.
- Credentials Hygiene: Pasted API keys and custom header values are stripped of line breaks, zero-width characters, the BOM, and control characters; several keys per provider rotate round-robin; keys travel only in headers, never in request URLs or logs, with one documented exception: Gemini Live accepts its key only as a URL query parameter, so that WebSocket URL is TLS-only (or loopback) and never logged. The provider client follows no redirects, so a key or request body never reaches a host the user did not configure. Custom headers are validated once in Rust (no credential, reserved, or line-break-carrying headers) and are cleared when a provider's origin changes.
- Untrusted Imports: Imported character cards pass `with_imported_permissions` (capability grants, MCP commands, and Windows UNC network paths removed; media restricted to `media/<name>`). The desktop open-folder bridge opens only existing local directories and refuses executables, shortcuts, and UNC shares. The file viewer hands a file to another app only if it is an existing local file that is not an executable, script, or shortcut and whose path does not start with two slashes (UNC and `\\?\` paths); on Android only as a `content://` URI from the app's `FileProvider`, limited to chat files and the paste cache, with a read grant for that one file.
- Local Daemon IPC: The daemon's named pipe is granted only to the signed-in user and SYSTEM and refuses remote clients; the app talks to the daemon only after confirming the pipe (or Unix socket) is served by the same user account, so another local user cannot impersonate the daemon to receive chat or steering content. Frames are capped at 64 MiB and timed; the daemon is the only child started outside the kill-on-close containment (so a run survives closing the window), and it exits once no app is attached and no work is live. Only one process writes a data folder (`daemon.lock`), so the app never opens the database while a daemon holds it.
- Workspace Hooks and Imports: Commands in a workspace's `.bistre/hooks.json` never run until the user approves that exact file (by content digest; any edit asks again), and an unapproved or failing pre-tool hook blocks the tool. A provider share code (`ai-provider:v1:`) leaves the API key out unless the user turns on `Include the API key`; importing one always makes a new provider, accepts only an `http(s)` server URL, and is capped at 16 KiB. An imported settings file cannot loosen the trust preset or the spending limit without the user confirming, and an unreadable tool-permission map allows only read-only tools.
- Tool Approvals: Every executed tool call claims a one-use permit bound to its exact arguments; any settings change revokes outstanding permits synchronously. A live approval answers exactly one paused call (thread + run + call id). "Approve for chat" re-allows only the identical call (any arguments only for Tier-0 reads), a denied call is not asked again in the same run, Stop cancels the run, and an unanswered approval waits without auto-approving or auto-denying.
- Release Signing: Android APKs are signed in a separate release job that alone holds the keystore and refuses to publish unless the APK carries exactly one signer matching the pinned release certificate (SHA-256 `AF:EC:66:EA:61:57:A7:62:F4:F9:DE:7D:BB:78:B4:66:A9:AD:3B:A4:C7:0E:7C:95:C5:C8:70:F9:57:2E:04:BC`); a CI build never falls back to the debug key silently. Windows builds are not Authenticode-signed; verify them with the release SHA-256 sums and Sigstore attestations.
- Android Build Supply Chain: Gradle dependency verification (`apps/bistre_app/android/gradle/verification-metadata.xml`, sha256 for every artifact, module, and POM the release build resolves) fails the build on any changed or unlisted dependency; refreshing it is a reviewed change (CONTRIBUTING).
- OTA Supply Chain: Every Track-A data pack and Track-B release manifest is verified offline with `minisign-verify` (Ed25519) before staging; the release manifest (format 2) is written and checked before publishing by the same Rust types the app reads; payloads require a SHA-256 digest, HTTPS, and a 256 MiB streamed cap; releases carry GitHub Sigstore build provenance attestations. Android publishes a single direct GitHub `arm64-v8a` APK with `PackageInstaller` verification and pinned APK signing-certificate SHA-256 checks.

## Reporting a Vulnerability
Please report security issues privately via GitHub Security Advisories on this repository rather than opening a public issue. Include reproduction steps, affected platform/version, and impact assessment.
